### 【知识储备】
#### 一、工具调用基础原理与配置
大模型擅长理解、概括和生成，但它并不天然具备现实世界中的执行能力。对于一个企业级 Agent 来说，获取实时外部数据、做确定性计算、查询业务系统、发送消息或写入文件，都不是模型单靠语言能力就能完成的事情。工具调用的意义，就是把模型的语言能力与系统的执行能力连接起来。一个典型的工具调用过程通常包括：
判断当前任务是否需要工具。
从候选能力中选择合适工具。
生成调用参数。
执行工具。
将结果写回上下文。
基于结果继续推理或输出。
工具调用并不是让模型随便调接口，而是一种让模型处于约束条件下的行动决策。工具描述、参数表单、返回结构和失败兜底，都会直接影响调用质量。
##### 1. 内置工具与 Function Calling
在RAGflow的平台实践中，学员可能接触到两类能力：
平台内置工具：接入门槛低，适合快速体验。
Function Calling或自定义函数：灵活度高，更适合贴合业务需求。
两者共同的工程要求都是需要清晰的输入输出，最好以结构化的方式明确字段类型并稳定输出内容，且必须有兜底结果应对失败场景。如果工具返回的是长篇原始文本，后续节点往往很难消费；如果返回的是结构化字段，则工作流更容易稳定运行。这是工具设计里非常重要的一个工程判断。
##### 2. 工具调用的门控机制
对低代码工作流而言，工具调用前的门控机制是非常基础、却又最容易缺失的一层设计。很多学员在接好工具之后，会本能地把用户输入直接连到工具节点，希望系统“边理解边执行”。这种做法在演示里偶尔能跑通，但在真实任务里非常容易失控。
更专业的做法是先做门控，再做调用。所谓门控，就是在进入工具节点前，先判断当前任务是否已经具备执行条件。对于本任务的市场需求分析场景来说，至少应先确认产品方向、行业范围、关注主题等关键信息是否齐全；如果条件还不够，就应先走追问分支，而不是勉强发起调用。
结合 RAGFlow的IF节点可以很好地实现门控机制，学员需要理解，IF节点在这里并不只是流程语法，而是在承担“执行授权”的作用。只有当前置条件满足时，工具节点才获得执行资格。这样做的价值主要有三点：
(1) 减少无意义调用，避免接口被错误触发。
(2) 提高参数质量，降低调用失败率。
(3) 让后续排障更清晰，知道问题到底出在条件判断还是调用本身。
学员须借此建立一个认知：工作流中的每一次外部调用，都应该被看作有成本、有风险的动作，而不是模型想到就做的随手行为。
#### 二、Agent Skill
##### 1. Agent Skill的概念
Agent Skill是2025年由Anthropic公司提出的概念，旨在解决复杂Agent系统中能力复用与组合的问题，目前已成为行业中的标准设计模式。Skill是一个模块化、可复用、可组合的能力包，能够被AI Agent按需加载和调用。与传统的把所有规则写在一个提示词里不同，Skill将某类任务相关的指令、资源和工具封装成一个独立的单元。Skill与其他概念的区别可以从表xxx中看到。
概念
核心作用
特点
Prompt
对单次推理的语言约束
面向模型输出，不可跨任务复用
Tool
对外部执行能力的调用接口
通常是函数、API或脚本，无内嵌规则
Skill
围绕某类任务沉淀的可复用能力单元
包含指令、资源、示例，可组合使用
从软件工程角度看，Skill对应了关注点分离与高内聚低耦合的设计原则。模块化的设计让每项能力边界清晰，独立开发、测试、版本管理。且同一个Skill可以在多个Agent或流程中被按需复用加载，避免重复劳动的同时减少常驻上下文占用。多个Skill也可以像积木一样组合，形成更复杂的能力。
##### 2. Skill的三层架构
根据2026年的工程最佳实践，一个规范的Skill通常包含以下三层结构：
架构层
内容
作用
元数据
Skill名称、简要描述、适用场景、版本号等
用于Agent发现和选择哪个Skill适合当前任务
指令层
详细的执行规则、约束条件、步骤分解、输出格式要求等
在Skill激活时加载到上下文中，指导模型的行为
资源层
具体的数据、工具函数、Few-shot示例、模板、API密钥等
在Skill执行时被调用，提供实际运行所需的素材
这一架构的设计思想是分层解耦：元数据用于发现，指令用于行为约束，资源用于实际执行。三层各有侧重，便于独立演进。
##### 3. Skill的输入输出接口设计
一个可复用的Skill必须明确其输入输出的形式与规则。这类似于编程中函数的签名（signature）。接口定义不清的Skill会变成黑盒，难以被其他开发者或Agent正确调用。以下是一个规范定义的示例：
```
Skill: 行业新闻摘要生成
输入:
- news_list: 新闻列表（JSON数组）
- focus_keywords: 关注关键词（字符串数组）
- output_format: 输出格式，可选值：markdown / json
规则:
- 每条新闻提取：标题、时间、来源、摘要（若原文无摘要则自动生成30字以内的概括）
- 突出显示包含任一关注关键词的内容（使用**粗体**或单独标记）
- 按时间倒序排列新闻条目
- 生成3条关键洞察，每条不超过20字
输出:
- summary: 结构化摘要对象
- total_count: 新闻总数（整数）
- key_insights: 关键洞察列表（字符串数组）
- news_items: 新闻条目列表
每一条包含：title, time, source, abstract, highlighted_keywords
```
与软件开发类似，接口设计是Skill能否被复用的关键。如果输入输出不明确，后续组合或替换Skill时会非常困难。在实践中，可以先从最简单的“输入→处理→输出”模式开始，逐步增加校验、异常处理和版本管理。
##### 4. 适合封装的逻辑
(1) 是否多次使用
如果它仅仅在当前这一次对话流程中才会用到，换一个场景就毫无意义，那就没有必要为它单独建立Skill。相反，如果同样的处理步骤在多个业务场景、不同用户请求中都会出现，那么把它固化下来，就避免了每次都重新描述规则的重复劳动。比如需求标准化，用户的原始输入往往是口语化、模糊甚至带有歧义的，将其转化为结构化的任务参数，这样的转换逻辑会在几乎每一个意图理解环节中被调用，天然适合封装。再比如数据清洗，将原始JSON或CSV中的空值、格式不一致等问题统一处理成规范的业务对象，这一步骤无论是在报表生成、分析还是导出场景中都会反复出现。还有结果摘要生成，把来自检索片段、表格等不同源头的信息整合为一份清晰的Markdown报告，这种能力一旦做好，就可以在多个下游任务中直接调用。多语言翻译也是同样，只要业务需要将中文内容稳定地输出为英文并保持术语一致，这个翻译Skill就可以在聊天、文档处理、邮件生成等多个流程中持续发光发热。
(2) 输入输出是否稳定
Skill的本质类似于编程中的函数，函数要想被放心地调用，就必须有明确、可靠的签名。这意味着它的输入参数要类型明确、结构固定，不能这一次接收的是字符串，下一次又要求一个复杂的嵌套对象，而且参数的含义不能随上下文忽而改变。同时，输出结构也应当相对确定，调用者能够稳定地预期会得到什么格式的结果，而不需要每次都去猜测。如果一个逻辑的输入高度依赖于当前对话的瞬时状态，比如“把上一轮回答中的第二个数字加1”，这种指令与特定对话历史紧紧绑在一起，换一个对话就完全失效，那就很难作为一个独立的Skill来设计。还有一些逻辑本身过于简单，一句代码就能完成的类型转换，把它封装成Skill虽然形式上满足输入输出稳定，但实际上增加了调用链的复杂度，得不偿失，这就不满足复用和维护的收益门槛。
(3) 是否值得单独维护
一个适合封装的Skill，应当是相对独立的，它不与其他能力高度耦合，职责清晰。同时，我们需要预见到它在未来有迭代优化的可能，比如数据清洗规则会随着业务变化而调整，或者翻译术语库需要持续更新。将这些逻辑聚拢在一个Skill内部，后续的修改就只需要在一个地方进行，不会牵一发而动全身。相反，如果某段逻辑只在一个特定流程里用一次，且未来几乎不会再变，单独把它抽出来反而会增加项目的理解和导航成本。

##### 步骤三 处理上传的csv文件
我们看到返回的内容不止有字典格式给出的文本内容，也有这个文件的相关信息，因此我们还需要对这段文本进行清洗，才能给后续节点使用。
在智能体工作流中我们很容易想到直接让智能体帮我们处理文件并给出最终结果，但这会占用大量的Token和上下文资源，因此在这一步我们通过调用代码工具来实现。创建一个代码节点，传入参数设置为这个csv文件，把它从文本转换为json列表的格式，最后设置输出格式为object。

```
REQUIRED_FIELDS = [
"country", "code", "region", "year",
"ev_sales", "ev_sales_share", "ev_stock",
"source_name", "source_url", "license"
]
def main(uploaded_file_content):
text = uploaded_file_content[0]
text = text.split("Content as following:", 1)[1].strip()
rows = []
for line in text.splitlines():
line = line.strip()
if not line:
continue
row = {}
parts = [p.strip() for p in line.split(";") if p.strip()]
for part in parts:
if "：" in part:
key, value = part.split("：", 1)

if row:

return {
"row_count": len(rows),
```

添加如下的筛选及排序代码，并设置输入输出变量和类型。

```
def main(csv_file):
rows = csv_file.get("rows")
year = 2024
metric = "ev_sales_share"
top_n = 5
region = "Europe"
filtered = [r for r in rows if int(r["year"]) == year]
if region and region != "Global":
filtered = [r for r in filtered if r["region"] == region]
filtered.sort(key=lambda x: float(x[metric]), reverse=True)
return {
"analysis_type": "topn_ranking",
"year": year,
"metric": metric,
"items": filtered[:top_n]
}
```

##### 步骤五 验证文件
在工程项目中，文件不会像课程用例一样标准，可能会有缺失值、格式错误、文件失效等问题，所以我们可以在预处理数据的同时添加验证逻辑，如果文件有问题，将它引导其他路由中。这部分逻辑可以通过修改代码模块实现：
```
REQUIRED_FIELDS = [
"country", "code", "region", "year",
"ev_sales", "ev_sales_share", "ev_stock",
"source_name", "source_url", "license"
]
def main(uploaded_file_content):
if not uploaded_file_content:
return {"ok": False, "message": "上传内容为空", "rows": []}
text = uploaded_file_content[0]
if "Content as following:" in text:
text = text.split("Content as following:", 1)[1].strip()
rows = []
for line in text.splitlines():
line = line.strip()
if not line:
continue
row = {}
parts = [p.strip() for p in line.split(";") if p.strip()]
for part in parts:
if "：" in part:
key, value = part.split("：", 1)
elif ":" in part:
key, value = part.split(":", 1)
else:
continue
row[key.strip()] = value.strip()
if row:
rows.append(row)
if not rows:
return {"ok": False, "message": "未解析出有效数据", "rows": []}
fieldnames = list(rows[0].keys())
missing = [f for f in REQUIRED_FIELDS if f not in fieldnames]
if missing:
return {
"ok": False,
"message": f"缺少字段: {', '.join(missing)}",
"rows": rows
}
return {
"ok": True,
"message": "文件加载成功",
"row_count": len(rows),
"rows": rows
}
```
