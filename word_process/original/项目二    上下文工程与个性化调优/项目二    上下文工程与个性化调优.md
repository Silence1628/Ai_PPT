### 【情境导入】
某制造企业希望为市场与产品部门上线一个“行业情报助手”。这个助手的目标并不复杂：每天自动获取指定行业的公开资讯，对结果进行筛选与摘要，再生成一份适合管理层阅读的简报，必要时还要发送到邮箱或企业消息渠道。
项目一开始，团队的想法很直接：既然大模型已经很强，那就给它一个Prompt，比如“请帮我整理今天的行业动态并生成报告”。但真正测试后很快发现，问题并不在于模型会不会写报告，而在于它根本拿不到实时数据，也不知道什么时候该自己回答，什么时候该调用外部能力。即便后来接入了某些工具，系统仍然会出现调用时机不对、参数生成不稳定、结果格式无法复用等问题。
团队这才意识到，企业级 Agent 的难点并不是“让模型说得更像人”，而是“让系统在正确的时候，把正确的能力和正确的信息组织给模型”。这正是上下文工程要解决的问题。
请思考：
1. 为什么一个写得不错的Prompt，仍然无法让Agent获得实时外部信息？
2. 为什么真实Agent的关键难点，不是有没有工具，而是会不会在正确时机调用工具？
3. 在一个任务里，哪些信息应该预先放进上下文，哪些信息应在执行过程中动态补充？

### 【知识储备】
#### 一、上下文工程
上下文工程（Context Engineering）是设计和管理模型在推理时所看到的全部信息的学科。它不仅仅关注提示词本身，而是关注整个上下文窗口的内容，包括系统指令、工具定义、检索文档、对话历史和注入的记忆。
让我们通过Anthropic团队的定义来深入理解：
```
"上下文工程是从不断演变的可能信息宇宙中，精心策划将进入有限上下文窗口的内容的艺术和科学。"
```
这个定义中有三个关键词值得我们深入思考：
"策划"（Curating）：这意味着上下文工程不是简单地把信息堆砌在一起，而是需要精心选择、组织和呈现信息。就像博物馆策展人需要从海量藏品中选择最能表达主题的展品一样，上下文工程师需要从海量可能相关的信息中选择最有价值的内容。
"有限"（Limited）：即使最先进的大模型，其上下文窗口也是有限的。Claude Opus 4.6提供了100万token（约75万词）的上下文窗口，这听起来很多，但在实际应用中，一个30分钟的客户支持对话，加上工具调用、知识检索和记忆注入，就可能轻松消耗50,000+个token。更重要的是，更多并不总是更好。
"演变"（Evolving）：在一个真实的Agent系统中，可能相关的信息是动态变化的。用户的每一次输入、每一次工具调用的结果、每一个新的记忆片段，都在改变着信息的相关性。上下文工程需要在这个动态的环境中持续做出决策。
##### 1. 上下文工程的核心特征
理解上下文工程，需要把握它的三个核心特征：
(1) 动态性（Dynamic）
传统的提示词工程往往使用静态模板——编写一次提示词，然后在所有场景下使用相同的模板。而上下文工程强调动态组装：每次模型推理时，系统都会根据当前的任务状态、用户特征、对话历史等因素，重新组装上下文窗口的内容。
举个例子，当用户第一次询问“帮我查询今天的新能源汽车行业动态”时，上下文中可能只包含：
```
- 系统角色定义
- 用户的当前输入
- 任务理解的指引
```
但当用户在第三轮对话中补充"只关注国内市场的融资信息"时，上下文会动态更新为：
```
- 系统角色定义
- 完整的对话历史（包含用户的逐步澄清）
- 已收集的任务参数（主题、市场范围、内容类型）
- 相关工具的定义（新闻查询API）
- 下一步执行的指引
```
(2) 系统性（Systematic）
上下文工程不是孤立地优化某一个部分，而是需要系统化地管理多个维度的信息：
上下文维度
对应的信息
检索维度
从知识库中检索哪些文档？检索多少？如何排序？
记忆维度
注入哪些历史记忆？如何平衡短期和长期记忆？
工具维度
暴露哪些工具？如何描述工具能力？
历史维度
保留多少对话历史？如何压缩早期对话？
指令维度
系统指令如何组织？如何与其他信息协调？
这些维度不是独立的，而是相互影响、相互制约的。例如，如果你决定检索更多的知识文档，就需要相应减少对话历史的保留量，以保持在token预算之内。
(3) 资源约束性（Resource-Constrained）
上下文工程的一个核心挑战是：上下文窗口是一种稀缺资源。这种稀缺性体现在三个方面：
Token数量限制：即使是最大的上下文窗口，也有其上限
成本约束：更长的上下文意味着更高的API调用成本
注意力稀释：Transformer架构的注意力机制会随着上下文长度的增加而稀释
因此，上下文工程的核心任务之一，就是在有限的资源约束下，最大化信息的价值密度。
##### 2. 上下文工程与提示词工程的本质区别
很多初学者会问：上下文工程和提示词工程有什么区别？它们是替代关系还是互补关系？让我们通过一个详细的对比来理解。
提示词工程关注如何写好一段指令文本，让模型理解你的意图并按照你的要求输出。它的核心问题是：我应该如何对模型说话？
而上下文工程关注模型在执行任务时能够"看到"的全部信息环境。它的核心问题是：模型需要看到什么信息才能完成这个任务？
用一个客户服务场景可以来说明这种差异，假设用户问：“我上次订购的商品什么时候能到？”从提示词工程的角度，可能会首先选择优化系统提示词：
```
你是一个专业的客户服务助手。当用户询问订单信息时，你应该：
1. 礼貌地回应用户
2. 提供准确的物流信息
3. 如果有延误，主动说明原因并致歉
```
这个提示词写得很好，但它无法解决一个根本问题：模型不知道"上次订购的商品"是什么，也不知道物流状态。因此，从上下文工程的角度，解决这个问题需要构建一个完整的信息环境：
```
[系统指令]
你是一个专业的客户服务助手...
[用户信息]
用户ID: 12345
用户姓名: 张三
会员等级: 金卡
[最近订单]
订单号: ORD--001
商品: iPhone 15 Pro
下单时间:  14:30
当前状态: 运输中
预计送达:
[物流信息]
快递公司: 顺丰速运
运单号: SF1234567890
最新位置: 北京分拨中心
更新时间:  09:00
[用户当前输入]
我上次订购的商品什么时候能到？
```
现在，模型拥有了回答这个问题所需的全部信息。这就是上下文工程和提示词工程的本质区别。理解了这些差异后，我们需要明确：上下文工程不是要替代提示词工程，而是它的工程化扩展。提示词工程中的各种技巧——思维链（Chain-of-Thought）、少样本学习（Few-Shot Learning）、角色提示（Role Prompting）——仍然非常有价值。但这些技巧需要在一个精心设计的上下文环境中才能发挥最大效用。
##### 3. 上下文窗口的限制与挑战
根据LangChain在2026年发布的《Agent工程状态报告》，目前有57%的组织已经将Agent部署到生产环境。这个数字看起来令人鼓舞，但报告同时揭示了一个严峻的现实：在大型企业中，"质量"仍然是扩展Agent应用的首要障碍，有32%的受访者明确提到了这一点。
报告特别指出"上下文工程和大规模管理上下文"是企业面临的持续困难。换句话说，大多数团队都能让Agent的演示版本工作起来，但要将其推向生产环境并保持稳定的质量，上下文管道的设计和管理成为了关键的分水岭。
这个现象背后的原因是什么？让我们通过一个典型的案例来理解。假设你正在开发一个客户支持Agent。在演示环境中，它表现得很好：能够理解用户问题，查询相关信息，给出合理的回答。但当你将它部署到生产环境，处理真实的客户对话时，问题开始出现：
问题1：Agent产生幻觉
```
客户问："你们的退货政策是什么？"Agent回答："我们提供30天无理由退货。"但实际上，公司的政策是14天。为什么会这样？
原因可能是：
- 知识库中有过时的信息（公司曾经是30天政策）
- 检索系统没有优先返回最新的政策文档
- 上下文中没有明确标注信息的时效性
- 模型基于训练数据中的常见做法进行了推测
```
问题2：Agent忘记之前的对话
```
客户在第一轮说："我想退货。"Agent询问订单号。客户在第二轮提供了订单号。但到了第三轮，当客户问"退款什么时候到账"时，Agent却回答"请先告诉我您的订单号"。
原因可能是：
- 对话历史没有被正确保留
- 历史压缩算法丢失了关键信息
- 上下文窗口被其他信息占满，历史对话被截断
- 状态管理机制没有正确记录已收集的信息
```
问题3：Agent忽略可用工具
```
系统中配置了"查询订单状态"的工具，但当客户问"我的订单到哪了"时，Agent却回答"抱歉，我无法查询订单信息"。
原因可能是：
- 工具定义被放在上下文的中间位置，被模型忽略了
- 工具描述不够清晰，模型没有理解其适用场景
- 上下文中同时加载了太多工具，模型无法有效选择
- 工具定义的token占用过多，被动态裁剪掉了
```
这些问题的共同特点是：它们都不是提示词本身的问题，而是整个上下文管理系统的问题。即使是最先进的模型，其上下文窗口也有明确的上限。Claude Opus 4.6提供了100万token（约75万词）的上下文窗口，GPT-4 Turbo提供了128K token。这些数字看起来很大，但在实际应用中，消耗速度可能超出你的想象。
而更多的上下文并不总是带来更好的结果。Google的研究团队进行了"大海捞针"（Needle in a Haystack）实验：他们在不同长度的上下文中埋入一个特定的事实，然后测试模型能否准确检索这个事实。结果显示：
在20%上下文利用率时，模型能够可靠地检索到目标事实
在50%上下文利用率时，检索准确率开始下降
在80%上下文利用率时，同样的事实可能完全被忽略
更糟糕的是，研究还发现了"迷失在中间"（Lost in the Middle）效应：埋在上下文窗口中间三分之一位置的信息，最容易被模型忽略。模型对上下文开头和结尾的信息更加敏感。这意味着：一个精心策划的30K token上下文，可能比一个粗心组装的120K token上下文表现更好。
理解了这些限制和问题后，我们就能明白上下文工程的核心价值：通过合理组织上下文结构，将关键信息放在模型更容易关注的位置，提高模型对重要信息的利用效率，并且在保证质量的前提下，最小化token消耗，从而控制运营成本。
#### 二、上下文工程的核心原则
##### 1. 渐进式披露
渐进式披露（Progressive Disclosure）这个概念最初来自用户体验设计领域。在UX设计中，它指的是逐步向用户展示功能和信息，而不是一次性展示所有内容，避免信息过载导致用户困惑。
在上下文工程中，这个原则同样适用：我们应该逐步向模型提供信息，而不是一次性将所有可能相关的信息都塞进上下文窗口，一般遵循以下原则：
- 当前节点只注入当前任务真正需要的信息。
- 工具结果返回后，再将必要字段写入后续上下文。
- 无关信息不过度进入上下文。
假设我们正在构建一个行业情报助手，用户的任务是获取新能源汽车行业的最新动态。让我们看看在不同阶段，上下文应该包含什么内容。
(1) 第一轮对话：任务启动
用户输入："帮我整理今天的新能源汽车行业动态。"
此时的上下文应该包含：
```
[系统角色]
你是一个专业的行业情报助手，帮助用户收集和整理行业动态信息。
[任务理解指引]
当用户提出信息收集需求时，你需要：
1. 识别用户关注的行业主题
2. 确认用户需要的信息范围（市场、内容类型、时间范围等）
3. 如果信息不完整，主动询问以明确需求
[用户输入]
帮我整理今天的新能源汽车行业动态。
[当前任务状态]
- 主题：新能源汽车
- 市场范围：未指定
- 内容类型：未指定
- 时间范围：今天
- 数量限制：未指定
```
注意，在这个阶段，不需要加载的内容是：新闻查询工具的详细定义、数据处理的规则和流程、报告生成的模板以及历史查询记录，因为这些信息在当前阶段用不到，加载它们只会浪费token并分散模型的注意力。
(2) 第二轮对话：需求澄清
系统回复："好的，请问您更关注国内市场还是海外市场？"
用户输入："国内市场。"
此时的上下文更新为：
```
[系统角色]
（同上）
[对话历史]
用户：帮我整理今天的新能源汽车行业动态。
助手：好的，请问您更关注国内市场还是海外市场？
用户：国内市场。
[当前任务状态]
- 主题：新能源汽车
- 市场范围：国内 ✓
- 内容类型：未指定
- 时间范围：今天
- 数量限制：未指定
[下一步指引]
继续询问用户关注的内容类型（融资、政策、新品发布等）
```
仍然不需要加载工具定义和数据处理规则。
(3) 第三轮对话：需求完善
系统回复："明白了。您希望重点关注哪些方面？比如融资动态、政策法规、新品发布等？"
用户输入："融资和新品发布，只保留前10条。"
此时的上下文更新为：
```
[系统角色]
（同上）
[对话历史]
（压缩的历史摘要）
用户需求：整理今天国内新能源汽车市场的融资和新品发布动态，前10条。
[当前任务状态]
- 主题：新能源汽车
- 市场范围：国内 ✓
- 内容类型：融资、新品发布 ✓
- 时间范围：今天 ✓
- 数量限制：10 ✓
- 状态：需求完整，准备执行
[工具定义]
现在加载新闻查询工具：
工具名称：query_industry_news
功能：查询指定行业的最新资讯
参数：
- industry: 行业名称
- market: 市场范围
- content_types: 内容类型列表
- date_range: 时间范围
- limit: 结果数量上限
[执行指引]
使用query_industry_news工具获取数据，参数如下：
- industry: "新能源汽车"
- market: "国内"
- content_types: ["融资", "新品发布"]
- date_range: "today"
- limit: 10
```
注意，只有在需求完整、准备执行时，我们才加载工具定义。而且只加载当前需要的工具，不加载其他无关工具。
(4) 第四轮：数据处理
工具返回了10条新闻数据。现在上下文需要包含数据处理的指引：
```
[系统角色]
（同上）
[任务状态]
数据已获取，需要进行清洗和格式化
[原始数据]
（10条新闻的结构化数据，只保留关键字段：标题、来源、时间、摘要、链接）
[数据处理规则]
现在加载数据处理规则：
1. 验证数据完整性
2. 按时间倒序排列
3. 提取关键信息
4. 生成结构化摘要
[输出格式要求]
现在加载输出模板：
（Markdown格式的报告模板）
```
在这个阶段，工具定义可以从上下文中移除（因为已经完成调用），取而代之的是数据处理规则和输出格式要求。
通过上面的例子，我们可以看到清晰的上下文边界有助于模型理解当前处于任务的哪个阶段，应该做什么，避免模型的注意力被不必要的数据分散。这种清晰性提高了系统行为的可预测性和稳定性。
##### 2. 预算管理原则
在软件开发中，我们熟悉内存预算、CPU预算、网络带宽预算等概念。在上下文工程中，Token预算是一个同样重要但常被忽视的概念。Token预算管理的核心思想是：将有限的上下文窗口视为一种需要精心分配的资源，为不同类型的信息设定明确的使用上限，并在这些约束下优化信息的价值密度。
基于大量生产环境的实践经验，业界已经形成了一些经过验证的预算分配策略。对于面向客户的对话型Agent，推荐的分配比例是：
```
系统提示词层（20-30%）
├─ 角色定义
├─ 核心能力描述
└─ 关键约束规则
任务上下文层（40-60%）
├─ 用户当前问题
├─ 相关历史对话
└─ 检索知识片段
输出预留层（20-30%）
├─ 模型生成空间
├─ 思维链空间
└─ 应急缓冲区
```
上述分配比例只是一个基准。在实际应用中，我们需要根据任务类型动态调整预算分配。比如在客户服务场景中，用户强烈期望Agent能够记住他们说过的话，因此在该场景下，会分配更多的Token比例给对话历史。而如果任务需要引用大量专业知识，检索的文档数量和长度都会增加。相应地，可以适当减少对话历史的保留量，因为这类任务往往更关注当前问题而非长期对话。
#### 三、生产级上下文管道的五层架构
##### 1. 架构概览与设计哲学
如果我们把所有信息混在一起，不加区分地塞进上下文，会面临几个问题：
难以管理：不知道哪些信息来自哪里，难以更新和维护
难以优化：无法针对不同类型的信息采用不同的优化策略
难以调试：出问题时无法快速定位是哪部分信息有问题
分层架构解决了这些问题。每一层有明确的职责、独立的管理策略和清晰的接口。
系统层
描述
功能
系统指令 (Instructions)
模型应该如何行为
身份、规则、约束
检索知识 (Knowledge)
模型需要知道什么
外部知识、事实
持久记忆 (Memory)
模型应该记住什么
用户偏好、历史事实
对话历史 (History)
发生了什么
当前会话的上下文
工具定义 (Tool Definitions)
模型可以做什么
可用的能力
你可能注意到，这五层有明确的顺序。这个顺序不是随意的，而是基于模型的注意力机制精心设计的。
研究表明，包括大模型在内的Transformer模型对上下文中不同位置的信息关注度是不同的：
- 开头位置：模型给予较高关注（首因效应）
- 结尾位置：模型给予较高关注（近因效应）
- 中间位置：模型关注度较低（"迷失在中间"效应）
因此，我们应该将最重要、最稳定的信息放在开头（系统指令），将最相关、最动态的信息放在结尾（工具定义、当前输入），而辅助性信息放在中间（知识、记忆、历史）。
```
[开头 - 高关注度]
1. 系统指令 - 定义基本行为，需要始终被关注
2. 检索知识 - 当前任务的关键知识，重要性高
[中间 - 中等关注度]
3. 持久记忆 - 用户相关信息，重要但不紧急
4. 对话历史 - 上下文信息，需要但可以压缩
[结尾 - 高关注度]
5. 工具定义 - 当前可用的行动选项，需要立即关注
6. 用户当前输入 - 最新的需求，最高优先级
[最后]
7. 输出格式要求 - 确保模型按要求输出
```
这个顺序确保了最重要的信息能够得到模型的充分关注。
##### 2. 第一层：系统指令（System Instructions）
很多团队在编写系统指令时，会犯一个典型错误：试图在系统提示词中描述所有可能的场景和处理规则。结果是一个5000-10000 token的超长提示词，包含了：详细的业务流程说明、各种边缘情况的处理规则、大量的示例对话以及所有可能的错误处理方案。这样的系统提示词在模型还没有开始推理就消耗过多Token预算，并且系统提示词包含太多信息，模型可能无法有效抓住重点。Anthropic团队建议：系统指令应该是"完全定义Agent行为的最小token集合"。具体来说包括两部分：
(1) 核心部分（必须包含）
```
# 角色定义
你是一个专业的行业情报助手，帮助用户收集和整理行业动态信息。
# 核心能力
- 理解用户的信息需求
- 查询和检索相关行业资讯
- 整理和分析信息
- 生成结构化报告
# 行为准则
1. 主动澄清：当需求不明确时，主动询问以明确用户意图
2. 事实为本：所有信息必须基于可靠来源，不编造内容
3. 结构清晰：输出信息应该结构化、易于阅读
4. 及时反馈：在执行耗时操作前，告知用户正在进行的操作
# 约束条件
- 不提供投资建议或预测
- 不处理敏感或机密信息
- 信息来源必须可追溯
```
这个系统指令只有约200 tokens，但清晰地定义了Agent的核心行为。
(2) 动态部分（运行时注入）
以下是一个python方式编写的提示词案例，目的是将场景相关的信息在运行时动态注入：
```
def build_system_prompt(base_prompt, current_stage, user_context):
prompt = base_prompt
# 根据当前阶段添加特定指引
if current_stage == "requirement_collection":
prompt += "\n\n# 当前任务\n"
prompt += "你正在收集用户的信息需求。需要明确：主题、市场范围、内容类型、时间范围。"
elif current_stage == "execution":
prompt += "\n\n# 当前任务\n"
prompt += "需求已明确，现在执行信息检索。使用query_industry_news工具获取数据。"
# 注入用户相关的上下文
if user_context.get("preferences"):
prompt += f"\n\n# 用户偏好\n{user_context['preferences']}"
return prompt
```
这个函数的功能是将智能体在运行过程中获取的信息拼装到基础提示词中，这种动态组装的方式，既保持了系统指令的简洁，又提供了必要的灵活性。
##### 3. 第二层：检索知识（Retrieved Knowledge / RAG）
检索增强生成（RAG）是上下文工程五层架构中的第二层，它解决了一个核心问题：如何让模型访问其训练数据之外的知识。RAG的基本流程：
用户提出问题或任务
系统将问题转换为查询向量
在知识库中检索最相关的文档
将检索到的文档注入上下文
模型基于这些文档生成回答
传统RAG是被动的：用户问什么，系统就检索什么。而Agentic RAG则增加了主动性和智能性，可以先对用户问题进行一轮分析，判断是否需要更多信息，再根据信息做进一步检索。
RAGFlow的知识检索节点提供了RAG（Retrieval-Augmented Generation，检索增强生成）功能，是让智能体在回答前先从私有知识库或记忆库中检索相关的数据，再将检索结果提供给模型参考，从而输出更加专业的回复。如错误!未找到引用源。，使用此类知识检索的基本流程通常是：根据用户提出问题，将问题向量化或关键词化。然后从知识库中检索并召回若干相关文档片段，将召回结果作为上下文注入大模型。最后基于检索内容生成回答。
RAG不是“把整份文档塞给模型”，而是“先检索再注入”，这样做可以有效缓解模型对话中上下文紧缺的问题。另外，由于最后输出的结果会受到从知识库中检索出的文段影响，因此在构建知识库时的文档切分质量会直接影响模型效果，切得过碎会丢上下文，切得过大则会降低召回精度。
RAGFlow的知识检索节点
需要提醒的是，使用RAG的场景一般要求大模型的输出内容严格依照检索信息生成，因此通过提示词对模型进行约束，防止模型“幻觉”输出是一件十分重要的事：
```
请优先依据提供的知识库片段回答问题。
如果片段中没有足够依据，请明确说明“根据当前知识库内容无法确认”，不要自行补充未经检索支持的信息。
```
##### 4. 第三层：持久记忆（Persistent Memory）
在上下文工程中，记忆不是单一的概念，而是分为三个层次：
工作记忆
生命周期
当前任务执行期间
内容
任务状态、中间结果、临时变量
存储
内存中的状态对象
示例
已收集的参数、当前执行阶段
短期记忆
生命周期
当前会话
内容
对话历史、会话状态
存储
会话存储（Redis、内存数据库）
示例
最近10轮对话、用户本次提到的偏好
长期记忆
生命周期
跨会话持久化
内容
用户画像、历史交互、重要事实
存储
持久化数据库、向量数据库
示例
用户的职业、常问的问题类型、历史订单
不是所有记忆都应该在每次调用时注入上下文。我们需要在工作流设计中智能地选择相关记忆注入上下文。
##### 5. 第四层：对话历史（Conversation History）
对话历史是上下文中最容易失控的部分。一个30轮的对话，如果每轮1000 tokens，总共就是30,000 tokens。如果不加管理，很快就会耗尽上下文预算。但对话历史又是上下文中不可或缺的一部分记录，我们可以用以下三种策略管理历史对话：
(1) 最简单的方法：只保留最近N轮对话；
(2) 在流程中判断重要的对话轮次，保留重要轮次，压缩不重要的；
(3) 设置上下文阈值，将达到阈值或更早期的对话压缩为摘要。
##### 6. 第五层：工具定义（Tool Definitions）
在RAGFlow平台中已经完成了定义了内置工具，我们无需再对这些内容进行操作，但为了让学员了解上下文工程的生产级管理架构，我们仍需对这部分内容进行简单描述。
工具定义可以让智能体知道有什么可以直接使用的工具，从而对文本外部乃至系统中的文件产生影响。但我们在使用工具定义时，不要在每次调用时加载所有工具定义。而是要根据任务阶段和需求，动态选择相关工具：
```
def select_relevant_tools(current_stage, task_type, all_tools):
relevant_tools = []
if current_stage == "requirement_collection":
# 需求收集阶段不需要工具
return []
elif current_stage == "execution":
# 执行阶段加载任务相关的工具
if task_type == "news_query":
relevant_tools = [
all_tools["query_industry_news"],
all_tools["search_web"]
]
elif task_type == "data_analysis":
relevant_tools = [
all_tools["query_database"],
all_tools["run_analysis"]
]
elif current_stage == "notification":
# 通知阶段加载通知工具
relevant_tools = [
all_tools["send_email"],
all_tools["send_message"]
]
return relevant_tools
```
这段代码展示了通过条件判断用户意图，从而动态加载工具。此外，还需要保持工具定义的简洁性与完整性：
```
# 不好的工具描述（过于简单）
{
"name": "query_news",
"description": "查询新闻"
}
# 好的工具描述（清晰完整）
{
"name": "query_industry_news",
"description": "查询指定行业的最新资讯。返回新闻列表，每条包含标题、来源、时间、摘要和链接。适用于获取行业动态、市场信息、政策更新等场景。",
"parameters": {
"industry": {
"type": "string",
"description": "行业名称，如'新能源汽车'、'人工智能'",
"required": true
},
"date_range": {
"type": "string",
"enum": ["today", "week", "month"],
"description": "时间范围",
"default": "today"
}
}
}
```
我们可以通过格式化的文本（markdown或json）对工具进行清晰简洁的定义，这种文本格式也让智能体更容易识别。

### 【知识储备】
#### 一、工具调用基础原理与配置
大模型擅长理解、概括和生成，但它并不天然具备现实世界中的执行能力。对于一个企业级 Agent 来说，获取实时外部数据、做确定性计算、查询业务系统、发送消息或写入文件，都不是模型单靠语言能力就能完成的事情。工具调用的意义，就是把模型的语言能力与系统的执行能力连接起来。一个典型的工具调用过程通常包括：
判断当前任务是否需要工具。
从候选能力中选择合适工具。
生成调用参数。
执行工具。
将结果写回上下文。
基于结果继续推理或输出。
工具调用并不是让模型随便调接口，而是一种让模型处于约束条件下的行动决策。工具描述、参数表单、返回结构和失败兜底，都会直接影响调用质量。
##### 1. 内置工具与 Function Calling
在RAGflow的平台实践中，学员可能接触到两类能力：
平台内置工具：接入门槛低，适合快速体验。
Function Calling或自定义函数：灵活度高，更适合贴合业务需求。
两者共同的工程要求都是需要清晰的输入输出，最好以结构化的方式明确字段类型并稳定输出内容，且必须有兜底结果应对失败场景。如果工具返回的是长篇原始文本，后续节点往往很难消费；如果返回的是结构化字段，则工作流更容易稳定运行。这是工具设计里非常重要的一个工程判断。
##### 2. 工具调用的门控机制
对低代码工作流而言，工具调用前的门控机制是非常基础、却又最容易缺失的一层设计。很多学员在接好工具之后，会本能地把用户输入直接连到工具节点，希望系统“边理解边执行”。这种做法在演示里偶尔能跑通，但在真实任务里非常容易失控。
更专业的做法是先做门控，再做调用。所谓门控，就是在进入工具节点前，先判断当前任务是否已经具备执行条件。对于本任务的市场需求分析场景来说，至少应先确认产品方向、行业范围、关注主题等关键信息是否齐全；如果条件还不够，就应先走追问分支，而不是勉强发起调用。
结合 RAGFlow的IF节点可以很好地实现门控机制，学员需要理解，IF节点在这里并不只是流程语法，而是在承担“执行授权”的作用。只有当前置条件满足时，工具节点才获得执行资格。这样做的价值主要有三点：
(1) 减少无意义调用，避免接口被错误触发。
(2) 提高参数质量，降低调用失败率。
(3) 让后续排障更清晰，知道问题到底出在条件判断还是调用本身。
学员须借此建立一个认知：工作流中的每一次外部调用，都应该被看作有成本、有风险的动作，而不是模型想到就做的随手行为。
#### 二、Agent Skill
##### 1. Agent Skill的概念
Agent Skill是2025年由Anthropic公司提出的概念，旨在解决复杂Agent系统中能力复用与组合的问题，目前已成为行业中的标准设计模式。Skill是一个模块化、可复用、可组合的能力包，能够被AI Agent按需加载和调用。与传统的把所有规则写在一个提示词里不同，Skill将某类任务相关的指令、资源和工具封装成一个独立的单元。Skill与其他概念的区别可以从表xxx中看到。
概念
核心作用
特点
Prompt
对单次推理的语言约束
面向模型输出，不可跨任务复用
Tool
对外部执行能力的调用接口
通常是函数、API或脚本，无内嵌规则
Skill
围绕某类任务沉淀的可复用能力单元
包含指令、资源、示例，可组合使用
从软件工程角度看，Skill对应了关注点分离与高内聚低耦合的设计原则。模块化的设计让每项能力边界清晰，独立开发、测试、版本管理。且同一个Skill可以在多个Agent或流程中被按需复用加载，避免重复劳动的同时减少常驻上下文占用。多个Skill也可以像积木一样组合，形成更复杂的能力。
##### 2. Skill的三层架构
根据2026年的工程最佳实践，一个规范的Skill通常包含以下三层结构：
架构层
内容
作用
元数据
Skill名称、简要描述、适用场景、版本号等
用于Agent发现和选择哪个Skill适合当前任务
指令层
详细的执行规则、约束条件、步骤分解、输出格式要求等
在Skill激活时加载到上下文中，指导模型的行为
资源层
具体的数据、工具函数、Few-shot示例、模板、API密钥等
在Skill执行时被调用，提供实际运行所需的素材
这一架构的设计思想是分层解耦：元数据用于发现，指令用于行为约束，资源用于实际执行。三层各有侧重，便于独立演进。
##### 3. Skill的输入输出接口设计
一个可复用的Skill必须明确其输入输出的形式与规则。这类似于编程中函数的签名（signature）。接口定义不清的Skill会变成黑盒，难以被其他开发者或Agent正确调用。以下是一个规范定义的示例：
```
Skill: 行业新闻摘要生成
输入:
- news_list: 新闻列表（JSON数组）
- focus_keywords: 关注关键词（字符串数组）
- output_format: 输出格式，可选值：markdown / json
规则:
- 每条新闻提取：标题、时间、来源、摘要（若原文无摘要则自动生成30字以内的概括）
- 突出显示包含任一关注关键词的内容（使用**粗体**或单独标记）
- 按时间倒序排列新闻条目
- 生成3条关键洞察，每条不超过20字
输出:
- summary: 结构化摘要对象
- total_count: 新闻总数（整数）
- key_insights: 关键洞察列表（字符串数组）
- news_items: 新闻条目列表
每一条包含：title, time, source, abstract, highlighted_keywords
```
与软件开发类似，接口设计是Skill能否被复用的关键。如果输入输出不明确，后续组合或替换Skill时会非常困难。在实践中，可以先从最简单的“输入→处理→输出”模式开始，逐步增加校验、异常处理和版本管理。
##### 4. 适合封装的逻辑
(1) 是否多次使用
如果它仅仅在当前这一次对话流程中才会用到，换一个场景就毫无意义，那就没有必要为它单独建立Skill。相反，如果同样的处理步骤在多个业务场景、不同用户请求中都会出现，那么把它固化下来，就避免了每次都重新描述规则的重复劳动。比如需求标准化，用户的原始输入往往是口语化、模糊甚至带有歧义的，将其转化为结构化的任务参数，这样的转换逻辑会在几乎每一个意图理解环节中被调用，天然适合封装。再比如数据清洗，将原始JSON或CSV中的空值、格式不一致等问题统一处理成规范的业务对象，这一步骤无论是在报表生成、分析还是导出场景中都会反复出现。还有结果摘要生成，把来自检索片段、表格等不同源头的信息整合为一份清晰的Markdown报告，这种能力一旦做好，就可以在多个下游任务中直接调用。多语言翻译也是同样，只要业务需要将中文内容稳定地输出为英文并保持术语一致，这个翻译Skill就可以在聊天、文档处理、邮件生成等多个流程中持续发光发热。
(2) 输入输出是否稳定
Skill的本质类似于编程中的函数，函数要想被放心地调用，就必须有明确、可靠的签名。这意味着它的输入参数要类型明确、结构固定，不能这一次接收的是字符串，下一次又要求一个复杂的嵌套对象，而且参数的含义不能随上下文忽而改变。同时，输出结构也应当相对确定，调用者能够稳定地预期会得到什么格式的结果，而不需要每次都去猜测。如果一个逻辑的输入高度依赖于当前对话的瞬时状态，比如“把上一轮回答中的第二个数字加1”，这种指令与特定对话历史紧紧绑在一起，换一个对话就完全失效，那就很难作为一个独立的Skill来设计。还有一些逻辑本身过于简单，一句代码就能完成的类型转换，把它封装成Skill虽然形式上满足输入输出稳定，但实际上增加了调用链的复杂度，得不偿失，这就不满足复用和维护的收益门槛。
(3) 是否值得单独维护
一个适合封装的Skill，应当是相对独立的，它不与其他能力高度耦合，职责清晰。同时，我们需要预见到它在未来有迭代优化的可能，比如数据清洗规则会随着业务变化而调整，或者翻译术语库需要持续更新。将这些逻辑聚拢在一个Skill内部，后续的修改就只需要在一个地方进行，不会牵一发而动全身。相反，如果某段逻辑只在一个特定流程里用一次，且未来几乎不会再变，单独把它抽出来反而会增加项目的理解和导航成本。

##### 步骤三 处理上传的csv文件
我们看到返回的内容不止有字典格式给出的文本内容，也有这个文件的相关信息，因此我们还需要对这段文本进行清洗，才能给后续节点使用。
在智能体工作流中我们很容易想到直接让智能体帮我们处理文件并给出最终结果，但这会占用大量的Token和上下文资源，因此在这一步我们通过调用代码工具来实现。创建一个代码节点，传入参数设置为这个csv文件，把它从文本转换为json列表的格式，最后设置输出格式为object。
```
REQUIRED_FIELDS = [
"country", "code", "region", "year",
"ev_sales", "ev_sales_share", "ev_stock",
"source_name", "source_url", "license"
]
def main(uploaded_file_content):
text = uploaded_file_content[0]
text = text.split("Content as following:", 1)[1].strip()
rows = []
for line in text.splitlines():
line = line.strip()
if not line:
continue
row = {}
parts = [p.strip() for p in line.split(";") if p.strip()]
for part in parts:
if "：" in part:
key, value = part.split("：", 1)
elif ":" in part:
key, value = part.split(":", 1)
else:
continue
row[key.strip()] = value.strip()
if row:
rows.append(row)
return {
"row_count": len(rows),
"rows": rows
}
```
再次运行工作流上传文件，可以看到数据结果已经和我们设置的一样，形成了json格式的列表
##### 步骤四 分析表格数据
格式化后的表格数据对我们人类来说和原本的表格差别不大，所以为了更直观地看到表格中的数据，我们可以再用代码工具实现一个简单的数据分析功能，分析Europe区域中2024年ev_sales_share的前5名，并以简报的形式描述返回的结果。
要实现这一步，我们需要获取限定条件下ev_sales_share的前5名，这是一个排序功能，明白这一点后我们来添加第二个代码节点，实现该功能。为了和第一个区分开，我们分别给两个节点起名为“数据预处理”和“数据排序”。
添加如下的筛选及排序代码，并设置输入输出变量和类型。
```
def main(csv_file):
rows = csv_file.get("rows")
year = 2024
metric = "ev_sales_share"
top_n = 5
region = "Europe"
filtered = [r for r in rows if int(r["year"]) == year]
if region and region != "Global":
filtered = [r for r in filtered if r["region"] == region]
filtered.sort(key=lambda x: float(x[metric]), reverse=True)
return {
"analysis_type": "topn_ranking",
"year": year,
"metric": metric,
"items": filtered[:top_n]
}
```
执行到这里，我们获取到了分析需要的数据，接下来需要把数据整理成文稿，形成一篇简报，所以还需要添加一个智能体节点，配合系统提示词：
```
你是一名新能源汽车产业研究助理。
请根据输入的结构化分析结果`数据排序/content`分析，生成一份商务风格的 Markdown 简报。
要求：
1. 只基于输入数据写作；
2. 先给出 3 条关键发现；
3. 再给出明细列表；
4. 最后保留数据来源与许可说明；
5. 不得编造数据。
```
如图xxx，可以看到模型按照我们的要求生成简报。值得注意的是“数据排序”的返回结果有两个，一个是被我们设置为Object的result，另一个是string格式的content，如果要被代码处理，使用Object格式的变量传输可以方便我们调整格式，但如果被内置的条件节点、回复节点或智能体节点调用，要使用string格式变量更容易被节点接受。
##### 步骤五 验证文件
在工程项目中，文件不会像课程用例一样标准，可能会有缺失值、格式错误、文件失效等问题，所以我们可以在预处理数据的同时添加验证逻辑，如果文件有问题，将它引导其他路由中。这部分逻辑可以通过修改代码模块实现：
```
REQUIRED_FIELDS = [
"country", "code", "region", "year",
"ev_sales", "ev_sales_share", "ev_stock",
"source_name", "source_url", "license"
]
def main(uploaded_file_content):
if not uploaded_file_content:
return {"ok": False, "message": "上传内容为空", "rows": []}
text = uploaded_file_content[0]
if "Content as following:" in text:
text = text.split("Content as following:", 1)[1].strip()
rows = []
for line in text.splitlines():
line = line.strip()
if not line:
continue
row = {}
parts = [p.strip() for p in line.split(";") if p.strip()]
for part in parts:
if "：" in part:
key, value = part.split("：", 1)
elif ":" in part:
key, value = part.split(":", 1)
else:
continue
row[key.strip()] = value.strip()
if row:
rows.append(row)
if not rows:
return {"ok": False, "message": "未解析出有效数据", "rows": []}
fieldnames = list(rows[0].keys())
missing = [f for f in REQUIRED_FIELDS if f not in fieldnames]
if missing:
return {
"ok": False,
"message": f"缺少字段: {', '.join(missing)}",
"rows": rows
}
return {
"ok": True,
"message": "文件加载成功",
"row_count": len(rows),
"rows": rows
}
```
通过这套校验机制，配合图xxx的问题分类节点，可以把一些基础错误隔绝在工作流外。设置输入变量为string格式的`数据处理/content`，两个问题分类如红框所示，指代“ok”变量的结果，分别是True和False。错误结果的返回节点配置使用的输出变量同样是`数据处理/content`，因为在其中也有保存的信息。
这样在运行过程中给，就可以测试文件是否正常，能否以工作流需要的格式接收数据，将这些信息统一约定并校验有助于智能体工作流的搭建和扩展。学员可以将csv表格复制备份并删除其中一两行关键列，测试校验效果能否顺利执行。
