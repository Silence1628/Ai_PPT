### 【知识储备】
#### 一、上下文工程
上下文工程（Context Engineering）是设计和管理模型在推理时所看到的全部信息的学科。它不仅仅关注提示词本身，而是关注整个上下文窗口的内容，包括系统指令、工具定义、检索文档、对话历史和注入的记忆。
让我们通过Anthropic团队的定义来深入理解：
"上下文工程是从不断演变的可能信息宇宙中，精心策划将进入有限上下文窗口的内容的艺术和科学。"
这个定义中有三个关键词值得我们深入思考：
"策划"（Curating）：这意味着上下文工程不是简单地把信息堆砌在一起，而是需要精心选择、组织和呈现信息。就像博物馆策展人需要从海量藏品中选择最能表达主题的展品一样，上下文工程师需要从海量可能相关的信息中选择最有价值的内容。
"有限"（Limited）：即使最先进的大模型，其上下文窗口也是有限的。Claude Opus 4.6提供了100万token（约75万词）的上下文窗口，这听起来很多，但在实际应用中，一个30分钟的客户支持对话，加上工具调用、知识检索和记忆注入，就可能轻松消耗50,000+个token。更重要的是，更多并不总是更好。
"演变"（Evolving）：在一个真实的Agent系统中，可能相关的信息是动态变化的。用户的每一次输入、每一次工具调用的结果、每一个新的记忆片段，都在改变着信息的相关性。上下文工程需要在这个动态的环境中持续做出决策。
##### 1. 上下文工程的核心特征
理解上下文工程，需要把握它的三个核心特征：
(1) 动态性（Dynamic）
传统的提示词工程往往使用静态模板——编写一次提示词，然后在所有场景下使用相同的模板。而上下文工程强调动态组装：每次模型推理时，系统都会根据当前的任务状态、用户特征、对话历史等因素，重新组装上下文窗口的内容。
举个例子，当用户第一次询问“帮我查询今天的新能源汽车行业动态”时，上下文中可能只包含：
- 系统角色定义
- 用户的当前输入
- 任务理解的指引
但当用户在第三轮对话中补充"只关注国内市场的融资信息"时，上下文会动态更新为：
- 系统角色定义
- 完整的对话历史（包含用户的逐步澄清）
- 已收集的任务参数（主题、市场范围、内容类型）
- 相关工具的定义（新闻查询API）
- 下一步执行的指引
(2) 系统性（Systematic）
上下文工程不是孤立地优化某一个部分，而是需要系统化地管理多个维度的信息：
上下文维度
对应的信息
检索维度
从知识库中检索哪些文档？检索多少？如何排序？
记忆维度
注入哪些历史记忆？如何平衡短期和长期记忆？
工具维度
暴露哪些工具？如何描述工具能力？
历史维度
保留多少对话历史？如何压缩早期对话？
指令维度
系统指令如何组织？如何与其他信息协调？
这些维度不是独立的，而是相互影响、相互制约的。例如，如果你决定检索更多的知识文档，就需要相应减少对话历史的保留量，以保持在token预算之内。
(3) 资源约束性（Resource-Constrained）
上下文工程的一个核心挑战是：上下文窗口是一种稀缺资源。这种稀缺性体现在三个方面：
Token数量限制：即使是最大的上下文窗口，也有其上限
成本约束：更长的上下文意味着更高的API调用成本
注意力稀释：Transformer架构的注意力机制会随着上下文长度的增加而稀释
因此，上下文工程的核心任务之一，就是在有限的资源约束下，最大化信息的价值密度。
##### 2. 上下文工程与提示词工程的本质区别
很多初学者会问：上下文工程和提示词工程有什么区别？它们是替代关系还是互补关系？让我们通过一个详细的对比来理解。
提示词工程关注如何写好一段指令文本，让模型理解你的意图并按照你的要求输出。它的核心问题是：我应该如何对模型说话？
而上下文工程关注模型在执行任务时能够"看到"的全部信息环境。它的核心问题是：模型需要看到什么信息才能完成这个任务？
用一个客户服务场景可以来说明这种差异，假设用户问：“我上次订购的商品什么时候能到？”从提示词工程的角度，可能会首先选择优化系统提示词：
你是一个专业的客户服务助手。当用户询问订单信息时，你应该：
1. 礼貌地回应用户
2. 提供准确的物流信息
3. 如果有延误，主动说明原因并致歉
这个提示词写得很好，但它无法解决一个根本问题：模型不知道"上次订购的商品"是什么，也不知道物流状态。因此，从上下文工程的角度，解决这个问题需要构建一个完整的信息环境：
[系统指令]
你是一个专业的客户服务助手...
[用户信息]
用户ID: 12345
用户姓名: 张三
会员等级: 金卡
[最近订单]
订单号: ORD--001
商品: iPhone 15 Pro
下单时间:  14:30
当前状态: 运输中
预计送达:
[物流信息]
快递公司: 顺丰速运
运单号: SF1234567890
最新位置: 北京分拨中心
更新时间:  09:00
[用户当前输入]
我上次订购的商品什么时候能到？
现在，模型拥有了回答这个问题所需的全部信息。这就是上下文工程和提示词工程的本质区别。理解了这些差异后，我们需要明确：上下文工程不是要替代提示词工程，而是它的工程化扩展。提示词工程中的各种技巧——思维链（Chain-of-Thought）、少样本学习（Few-Shot Learning）、角色提示（Role Prompting）——仍然非常有价值。但这些技巧需要在一个精心设计的上下文环境中才能发挥最大效用。
##### 3. 上下文窗口的限制与挑战
根据LangChain在2026年发布的《Agent工程状态报告》，目前有57%的组织已经将Agent部署到生产环境。这个数字看起来令人鼓舞，但报告同时揭示了一个严峻的现实：在大型企业中，"质量"仍然是扩展Agent应用的首要障碍，有32%的受访者明确提到了这一点。
报告特别指出"上下文工程和大规模管理上下文"是企业面临的持续困难。换句话说，大多数团队都能让Agent的演示版本工作起来，但要将其推向生产环境并保持稳定的质量，上下文管道的设计和管理成为了关键的分水岭。
这个现象背后的原因是什么？让我们通过一个典型的案例来理解。假设你正在开发一个客户支持Agent。在演示环境中，它表现得很好：能够理解用户问题，查询相关信息，给出合理的回答。但当你将它部署到生产环境，处理真实的客户对话时，问题开始出现：
问题1：Agent产生幻觉
客户问："你们的退货政策是什么？"Agent回答："我们提供30天无理由退货。"但实际上，公司的政策是14天。为什么会这样？
原因可能是：
- 知识库中有过时的信息（公司曾经是30天政策）
- 检索系统没有优先返回最新的政策文档
- 上下文中没有明确标注信息的时效性
- 模型基于训练数据中的常见做法进行了推测
问题2：Agent忘记之前的对话
客户在第一轮说："我想退货。"Agent询问订单号。客户在第二轮提供了订单号。但到了第三轮，当客户问"退款什么时候到账"时，Agent却回答"请先告诉我您的订单号"。
原因可能是：
- 对话历史没有被正确保留
- 历史压缩算法丢失了关键信息
- 上下文窗口被其他信息占满，历史对话被截断
- 状态管理机制没有正确记录已收集的信息
问题3：Agent忽略可用工具
系统中配置了"查询订单状态"的工具，但当客户问"我的订单到哪了"时，Agent却回答"抱歉，我无法查询订单信息"。
原因可能是：
- 工具定义被放在上下文的中间位置，被模型忽略了
- 工具描述不够清晰，模型没有理解其适用场景
- 上下文中同时加载了太多工具，模型无法有效选择
- 工具定义的token占用过多，被动态裁剪掉了
这些问题的共同特点是：它们都不是提示词本身的问题，而是整个上下文管理系统的问题。即使是最先进的模型，其上下文窗口也有明确的上限。Claude Opus 4.6提供了100万token（约75万词）的上下文窗口，GPT-4 Turbo提供了128K token。这些数字看起来很大，但在实际应用中，消耗速度可能超出你的想象。
而更多的上下文并不总是带来更好的结果。Google的研究团队进行了"大海捞针"（Needle in a Haystack）实验：他们在不同长度的上下文中埋入一个特定的事实，然后测试模型能否准确检索这个事实。结果显示：
在20%上下文利用率时，模型能够可靠地检索到目标事实
在50%上下文利用率时，检索准确率开始下降
在80%上下文利用率时，同样的事实可能完全被忽略
更糟糕的是，研究还发现了"迷失在中间"（Lost in the Middle）效应：埋在上下文窗口中间三分之一位置的信息，最容易被模型忽略。模型对上下文开头和结尾的信息更加敏感。这意味着：一个精心策划的30K token上下文，可能比一个粗心组装的120K token上下文表现更好。
理解了这些限制和问题后，我们就能明白上下文工程的核心价值：通过合理组织上下文结构，将关键信息放在模型更容易关注的位置，提高模型对重要信息的利用效率，并且在保证质量的前提下，最小化token消耗，从而控制运营成本。
#### 二、上下文工程的核心原则
##### 1. 渐进式披露
渐进式披露（Progressive Disclosure）这个概念最初来自用户体验设计领域。在UX设计中，它指的是逐步向用户展示功能和信息，而不是一次性展示所有内容，避免信息过载导致用户困惑。
在上下文工程中，这个原则同样适用：我们应该逐步向模型提供信息，而不是一次性将所有可能相关的信息都塞进上下文窗口，一般遵循以下原则：
- 当前节点只注入当前任务真正需要的信息。
- 工具结果返回后，再将必要字段写入后续上下文。
- 无关信息不过度进入上下文。
假设我们正在构建一个行业情报助手，用户的任务是获取新能源汽车行业的最新动态。让我们看看在不同阶段，上下文应该包含什么内容。
(1) 第一轮对话：任务启动
用户输入："帮我整理今天的新能源汽车行业动态。"
此时的上下文应该包含：
[系统角色]
你是一个专业的行业情报助手，帮助用户收集和整理行业动态信息。
[任务理解指引]
当用户提出信息收集需求时，你需要：
1. 识别用户关注的行业主题
2. 确认用户需要的信息范围（市场、内容类型、时间范围等）
3. 如果信息不完整，主动询问以明确需求
[用户输入]
帮我整理今天的新能源汽车行业动态。
[当前任务状态]
- 主题：新能源汽车
- 市场范围：未指定
- 内容类型：未指定
- 时间范围：今天
- 数量限制：未指定
注意，在这个阶段，不需要加载的内容是：新闻查询工具的详细定义、数据处理的规则和流程、报告生成的模板以及历史查询记录，因为这些信息在当前阶段用不到，加载它们只会浪费token并分散模型的注意力。
(2) 第二轮对话：需求澄清
系统回复："好的，请问您更关注国内市场还是海外市场？"
用户输入："国内市场。"
此时的上下文更新为：
[系统角色]
（同上）
[对话历史]
用户：帮我整理今天的新能源汽车行业动态。
助手：好的，请问您更关注国内市场还是海外市场？
用户：国内市场。
[当前任务状态]
- 主题：新能源汽车
- 市场范围：国内 ✓
- 内容类型：未指定
- 时间范围：今天
- 数量限制：未指定
[下一步指引]
继续询问用户关注的内容类型（融资、政策、新品发布等）
仍然不需要加载工具定义和数据处理规则。
(3) 第三轮对话：需求完善
系统回复："明白了。您希望重点关注哪些方面？比如融资动态、政策法规、新品发布等？"
用户输入："融资和新品发布，只保留前10条。"
此时的上下文更新为：
[系统角色]
（同上）
[对话历史]
（压缩的历史摘要）
用户需求：整理今天国内新能源汽车市场的融资和新品发布动态，前10条。
[当前任务状态]
- 主题：新能源汽车
- 市场范围：国内 ✓
- 内容类型：融资、新品发布 ✓
- 时间范围：今天 ✓
- 数量限制：10 ✓
- 状态：需求完整，准备执行
[工具定义]
现在加载新闻查询工具：
工具名称：query_industry_news
功能：查询指定行业的最新资讯
参数：
- industry: 行业名称
- market: 市场范围
- content_types: 内容类型列表
- date_range: 时间范围
- limit: 结果数量上限
[执行指引]
使用query_industry_news工具获取数据，参数如下：
- industry: "新能源汽车"
- market: "国内"
- content_types: ["融资", "新品发布"]
- date_range: "today"
- limit: 10
注意，只有在需求完整、准备执行时，我们才加载工具定义。而且只加载当前需要的工具，不加载其他无关工具。
(4) 第四轮：数据处理
工具返回了10条新闻数据。现在上下文需要包含数据处理的指引：
[系统角色]
（同上）
[任务状态]
数据已获取，需要进行清洗和格式化
[原始数据]
（10条新闻的结构化数据，只保留关键字段：标题、来源、时间、摘要、链接）
[数据处理规则]
现在加载数据处理规则：
1. 验证数据完整性
2. 按时间倒序排列
3. 提取关键信息
4. 生成结构化摘要
[输出格式要求]
现在加载输出模板：
（Markdown格式的报告模板）
在这个阶段，工具定义可以从上下文中移除（因为已经完成调用），取而代之的是数据处理规则和输出格式要求。
通过上面的例子，我们可以看到清晰的上下文边界有助于模型理解当前处于任务的哪个阶段，应该做什么，避免模型的注意力被不必要的数据分散。这种清晰性提高了系统行为的可预测性和稳定性。
##### 2. 预算管理原则
在软件开发中，我们熟悉内存预算、CPU预算、网络带宽预算等概念。在上下文工程中，Token预算是一个同样重要但常被忽视的概念。Token预算管理的核心思想是：将有限的上下文窗口视为一种需要精心分配的资源，为不同类型的信息设定明确的使用上限，并在这些约束下优化信息的价值密度。
基于大量生产环境的实践经验，业界已经形成了一些经过验证的预算分配策略。对于面向客户的对话型Agent，推荐的分配比例是：
系统提示词层（20-30%）
├─ 角色定义
├─ 核心能力描述
└─ 关键约束规则
任务上下文层（40-60%）
├─ 用户当前问题
├─ 相关历史对话
└─ 检索知识片段
输出预留层（20-30%）
├─ 模型生成空间
├─ 思维链空间
└─ 应急缓冲区
上述分配比例只是一个基准。在实际应用中，我们需要根据任务类型动态调整预算分配。比如在客户服务场景中，用户强烈期望Agent能够记住他们说过的话，因此在该场景下，会分配更多的Token比例给对话历史。而如果任务需要引用大量专业知识，检索的文档数量和长度都会增加。相应地，可以适当减少对话历史的保留量，因为这类任务往往更关注当前问题而非长期对话。
#### 三、生产级上下文管道的五层架构
##### 1. 架构概览与设计哲学
如果我们把所有信息混在一起，不加区分地塞进上下文，会面临几个问题：
难以管理：不知道哪些信息来自哪里，难以更新和维护
难以优化：无法针对不同类型的信息采用不同的优化策略
难以调试：出问题时无法快速定位是哪部分信息有问题
分层架构解决了这些问题。每一层有明确的职责、独立的管理策略和清晰的接口。

你可能注意到，这五层有明确的顺序。这个顺序不是随意的，而是基于模型的注意力机制精心设计的。
研究表明，包括大模型在内的Transformer模型对上下文中不同位置的信息关注度是不同的：
- 开头位置：模型给予较高关注（首因效应）
- 结尾位置：模型给予较高关注（近因效应）
- 中间位置：模型关注度较低（"迷失在中间"效应）
因此，我们应该将最重要、最稳定的信息放在开头（系统指令），将最相关、最动态的信息放在结尾（工具定义、当前输入），而辅助性信息放在中间（知识、记忆、历史）。
[开头 - 高关注度]
1. 系统指令 - 定义基本行为，需要始终被关注
2. 检索知识 - 当前任务的关键知识，重要性高
[中间 - 中等关注度]
3. 持久记忆 - 用户相关信息，重要但不紧急
4. 对话历史 - 上下文信息，需要但可以压缩
[结尾 - 高关注度]
5. 工具定义 - 当前可用的行动选项，需要立即关注
6. 用户当前输入 - 最新的需求，最高优先级
[最后]
7. 输出格式要求 - 确保模型按要求输出
这个顺序确保了最重要的信息能够得到模型的充分关注。
##### 2. 第一层：系统指令（System Instructions）
很多团队在编写系统指令时，会犯一个典型错误：试图在系统提示词中描述所有可能的场景和处理规则。结果是一个5000-10000 token的超长提示词，包含了：详细的业务流程说明、各种边缘情况的处理规则、大量的示例对话以及所有可能的错误处理方案。这样的系统提示词在模型还没有开始推理就消耗过多Token预算，并且系统提示词包含太多信息，模型可能无法有效抓住重点。Anthropic团队建议：系统指令应该是"完全定义Agent行为的最小token集合"。具体来说包括两部分：
(1) 核心部分（必须包含）
# 角色定义
你是一个专业的行业情报助手，帮助用户收集和整理行业动态信息。
# 核心能力
- 理解用户的信息需求
- 查询和检索相关行业资讯
- 整理和分析信息
- 生成结构化报告
# 行为准则
1. 主动澄清：当需求不明确时，主动询问以明确用户意图
2. 事实为本：所有信息必须基于可靠来源，不编造内容
3. 结构清晰：输出信息应该结构化、易于阅读
4. 及时反馈：在执行耗时操作前，告知用户正在进行的操作
# 约束条件
- 不提供投资建议或预测
- 不处理敏感或机密信息
- 信息来源必须可追溯
这个系统指令只有约200 tokens，但清晰地定义了Agent的核心行为。
(2) 动态部分（运行时注入）
以下是一个python方式编写的提示词案例，目的是将场景相关的信息在运行时动态注入：
def build_system_prompt(base_prompt, current_stage, user_context):
prompt = base_prompt
# 根据当前阶段添加特定指引
if current_stage == "requirement_collection":
prompt += "\n\n# 当前任务\n"
prompt += "你正在收集用户的信息需求。需要明确：主题、市场范围、内容类型、时间范围。"
elif current_stage == "execution":
prompt += "\n\n# 当前任务\n"
prompt += "需求已明确，现在执行信息检索。使用query_industry_news工具获取数据。"
# 注入用户相关的上下文
if user_context.get("preferences"):
prompt += f"\n\n# 用户偏好\n{user_context['preferences']}"
return prompt
这个函数的功能是将智能体在运行过程中获取的信息拼装到基础提示词中，这种动态组装的方式，既保持了系统指令的简洁，又提供了必要的灵活性。
##### 3. 第二层：检索知识（Retrieved Knowledge / RAG）
检索增强生成（RAG）是上下文工程五层架构中的第二层，它解决了一个核心问题：如何让模型访问其训练数据之外的知识。RAG的基本流程：
用户提出问题或任务
系统将问题转换为查询向量
在知识库中检索最相关的文档
将检索到的文档注入上下文
模型基于这些文档生成回答
传统RAG是被动的：用户问什么，系统就检索什么。而Agentic RAG则增加了主动性和智能性，可以先对用户问题进行一轮分析，判断是否需要更多信息，再根据信息做进一步检索。
RAGFlow的知识检索节点提供了RAG（Retrieval-Augmented Generation，检索增强生成）功能，是让智能体在回答前先从私有知识库或记忆库中检索相关的数据，再将检索结果提供给模型参考，从而输出更加专业的回复。如错误!未找到引用源。，使用此类知识检索的基本流程通常是：根据用户提出问题，将问题向量化或关键词化。然后从知识库中检索并召回若干相关文档片段，将召回结果作为上下文注入大模型。最后基于检索内容生成回答。
RAG不是“把整份文档塞给模型”，而是“先检索再注入”，这样做可以有效缓解模型对话中上下文紧缺的问题。另外，由于最后输出的结果会受到从知识库中检索出的文段影响，因此在构建知识库时的文档切分质量会直接影响模型效果，切得过碎会丢上下文，切得过大则会降低召回精度。
RAGFlow的知识检索节点
需要提醒的是，使用RAG的场景一般要求大模型的输出内容严格依照检索信息生成，因此通过提示词对模型进行约束，防止模型“幻觉”输出是一件十分重要的事：
请优先依据提供的知识库片段回答问题。
如果片段中没有足够依据，请明确说明“根据当前知识库内容无法确认”，不要自行补充未经检索支持的信息。
##### 4. 第三层：持久记忆（Persistent Memory）
在上下文工程中，记忆不是单一的概念，而是分为三个层次：
工作记忆
生命周期
当前任务执行期间
内容
任务状态、中间结果、临时变量
存储

存储
会话存储（Redis、内存数据库）
示例
最近10轮对话、用户本次提到的偏好
长期记忆
生命周期
跨会话持久化

存储

不是所有记忆都应该在每次调用时注入上下文。我们需要在工作流设计中智能地选择相关记忆注入上下文。
##### 5. 第四层：对话历史（Conversation History）
对话历史是上下文中最容易失控的部分。一个30轮的对话，如果每轮1000 tokens，总共就是30,000 tokens。如果不加管理，很快就会耗尽上下文预算。但对话历史又是上下文中不可或缺的一部分记录，我们可以用以下三种策略管理历史对话：
(1) 最简单的方法：只保留最近N轮对话；
(2) 在流程中判断重要的对话轮次，保留重要轮次，压缩不重要的；
(3) 设置上下文阈值，将达到阈值或更早期的对话压缩为摘要。
##### 6. 第五层：工具定义（Tool Definitions）
在RAGFlow平台中已经完成了定义了内置工具，我们无需再对这些内容进行操作，但为了让学员了解上下文工程的生产级管理架构，我们仍需对这部分内容进行简单描述。
工具定义可以让智能体知道有什么可以直接使用的工具，从而对文本外部乃至系统中的文件产生影响。但我们在使用工具定义时，不要在每次调用时加载所有工具定义。而是要根据任务阶段和需求，动态选择相关工具：
def select_relevant_tools(current_stage, task_type, all_tools):
relevant_tools = []
if current_stage == "requirement_collection":
# 需求收集阶段不需要工具
return []
elif current_stage == "execution":
# 执行阶段加载任务相关的工具
if task_type == "news_query":
relevant_tools = [
all_tools["query_industry_news"],
all_tools["search_web"]
]
elif task_type == "data_analysis":
relevant_tools = [
all_tools["query_database"],
all_tools["run_analysis"]
]
elif current_stage == "notification":
# 通知阶段加载通知工具
relevant_tools = [
all_tools["send_email"],
all_tools["send_message"]
]
return relevant_tools
这段代码展示了通过条件判断用户意图，从而动态加载工具。此外，还需要保持工具定义的简洁性与完整性：

### 【任务小结】
本任务系统讲解了上下文工程（Context Engineering）的核心概念、基本原则及其在智能体系统中的实际应用机制。通过对系统指令、知识检索、对话历史、记忆管理和工具定义等关键要素的分析，学员能够深入理解大模型应用为何不仅要关注“如何提问”，更要重视为模型提供什么信息、以何种方式组织信息。在实践环节，引导学员基于RAGFlow平台完成从知识库构建、工作流设计到智能学习助手搭建与优化的全过程。本任务将上下文工程的理论方法与可视化工作流开发相结合，为学员掌握智能问答应用设计、提升Agent稳定性与可用性奠定了扎实基础。
