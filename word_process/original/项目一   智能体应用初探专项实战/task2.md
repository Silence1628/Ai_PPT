### 【知识储备】
#### 一、什么是提示词工程
提示词工程（Prompt Engineering）是指围绕LLM或 Agent 系统的输入指令进行设计、组织、约束与优化，从而让系统更稳定地完成目标任务的方法。它不是简单地提问技巧，而是一种面向结果的交互设计方法。
在传统的软件系统中，开发者通过代码定义执行逻辑；而在智能体工作流系统中，提示词往往承担了半结构化程序的作用。它不仅告诉模型“做什么”，还告诉模型“以什么身份做”“依据什么信息做”“按照什么规则做”“最后以什么格式输出”。因此，提示词本质上是在为智能体编写行为说明书。
##### 1. 从LLM到Agent：提示词如何驱动决策
LLM 本身擅长语言理解与生成，但它并不会天然知道当前系统的目标、边界和优先级。Agent 则是在 LLM 基础上叠加了记忆、规划、工具调用和行动能力的系统。此时，提示词起到的作用就不再只是发起一次对话，而是持续塑造Agent的决策逻辑。
例如，在一个客服智能体中，提示词可以规定：
你是售后服务助手，不是销售顾问。
先判断用户问题类别，再决定是否查询知识库。
若知识库无答案，不允许编造，必须明确告知“暂无法确认”。
输出必须包含“问题判断”、“处理建议”以及“是否需要人工介入”三个字段。
这几句话看似自然语言，实则已经在约束智能体的角色、流程、容错机制和输出结构。提示词写得越清晰，智能体的行为越可控；提示词写得越模糊，智能体越容易漂移。一个优质提示词，通常要兼顾以下三个目标：
确定性
确定性并不是要求模型每次一字不差，而是要求模型在相同输入下尽量给出风格稳定、结构稳定、结论边界稳定的回答。对于企业级智能体而言，稳定性往往比偶尔的一次惊艳回答更重要。
逻辑性
逻辑性是指提示词要让模型清楚：先做什么，再做什么；依据什么判断；遇到异常怎么办；什么情况下该拒绝回答。逻辑清楚，模型的中间推理和最终输出才不容易跳步。
效率
效率既包括模型响应效率，也包括开发效率和 Token 成本。一个优质提示词不应堆砌无关描述，而应在有限上下文内，把最关键的约束表达清楚。

#### 二、LLM的工作原理简述
要做好提示词工程，不能只会写指令，还要理解模型为什么会这样响应。大语言模型的核心机制并不是理解了真实世界后再回答，而是根据已有上下文，预测下一个最可能出现的词或 Token。正因为它是概率生成，所以提示词的表达方式会显著影响结果分布。
##### 1. 预测机制与概率分布
当我们输入一句提示词时，模型会把整段上下文编码成内部向量表示，然后基于训练中学到的模式，预测下一个 Token 的概率分布。如图 ，在“今天天气很”之后，模型可能会认为“好”“冷”“热”“不错”等词都有不同概率。最终输出什么，取决于上下文、模型参数以及采样方式。
图  大模型输出原理
这意味着模型输出不是从零开始编一个答案，而是基于上文判断下文概率最高的延续。因此如果提示词模糊，模型会在更多可能性中摇摆，输出更不稳定；反之如果提示词明确，概率空间被压缩，模型更容易落在期望答案附近。
##### 2. 添加限定词约束大模型
因此，提示词工程的核心之一，就是通过清晰的上下文和明确的约束，把模型的概率分布“收紧”到更可控的区域。许多初学者会认为，只要把任务说出来就够了。实际上，在大模型场景中，“说什么”只是目标层，“怎么说”决定了模型如何理解这个目标。
例如，下面两个提示词表面上都在要求总结文章：
V1：
```
帮我总结一下这篇文章。
```
V2：
```
你是一名面向企业管理者的信息分析助手。请阅读下文，并提炼出：
1. 核心观点；
2. 支撑观点的关键事实；
3. 对企业决策的启示。
输出控制在 200 字以内，使用正式、客观的书面语。
```
二者的差别不在是否要求总结，而在于第二种写法明确了身份、读者、提取维度、长度和风格，从而显著提升了输出质量。换句话说，模型并不是听懂一句话就能自动补全所有隐含要求，它更像一个极其强大但需要明确边界的执行者。提示词写法越清楚，模型越容易朝正确方向生成。
##### 3. 使用few-shot提示
更进一步，除了明确身份、维度、长度和风格外，还有一种更直接、更强大的“怎么说”方式：给模型提供示例（few-shot）。
仍以“总结文章”为例。即使你已经写好了第二种提示词（明确了身份、读者、提取维度和风格），模型在处理不同文章时，依然可能在某些细节上偏离预期——例如把“核心观点”写成了两句话，或者在企业启示部分写得过于空泛。这时，你可以在提示词中直接放入一个真实的输入输出示例，让模型照模板来回复。
比如，针对“总结文章”的任务，可以这样构造 few-shot 提示词：
```
下面是两个例子，展示了如何按要求总结一篇文章。
示例文章A：
“过去三年，某制造企业通过引入AI质检系统，将产品缺陷率从2.3%降至0.4%，每年节省返工成本约800万元。管理层认为，技术本身只是工具，真正的挑战在于产线工人的技能转型和质检流程的重构。”
示例总结A：
1. 核心观点：AI质检能显著降低缺陷率，但成功关键在于人员转型与流程重构。
2. 关键事实：缺陷率从2.3%降至0.4%；年节省成本800万元。
3. 企业决策启示：引入AI时需同步规划员工技能培训和流程调整，不能仅关注技术指标。
---
现在请按同样方式总结下文：
（待总结的新文章内容……）
```
将这段提示词复制到步骤（2）中第V2版提示词的末尾。通过这个few-shot示例，模型不仅知道你要什么维度的信息，还看到了每个维度应该写多长、用什么句式、观点和事实如何分离。相比于只有指令的第二版提示词，加上few-shot后，输出的稳定性和一致性会再次明显提升。
#### 三、结构化提示词与版本管理
##### 1. 结构化的系统提示词
在构建大模型的系统提示词时，结构化设计是确保模型输出稳定性、准确性和专业性的核心。相比于碎片化的指令，结构化的提示词能够为模型建立一个清晰的逻辑框架。其核心思想是将复杂的任务拆解为若干个标准化的模块。通过清晰的分隔符和逻辑层次，引导模型更精准地理解意图。一个成熟的结构化提示词通常包含以下五个核心模块：
角色设定 (Role)：定义模型的身分。
```
你是一位拥有10年经验的资深资深文案策划专家，擅长撰写高转化率的社交媒体推文。
```
背景信息 (Context)：提供任务的上下文或目标受众。
```
我们正在推广一款针对职场新人的自律打卡App，其核心卖点是‘趣味化社交’。
```
任务目标 (Task)：明确模型需要执行的具体动作。
```
请根据产品卖点，撰写3条不同风格的推文文案。
```
约束与规则 (Constraints)：规定“能做”和“不能做”的边界。
```
语言风格需轻松活泼；禁止使用虚假宣传词汇；每条文案长度不超过150字。
```
输出格式 (Output)：规定返回结果的形式。
```
请按【风格关键词】、【推文内容】、【建议配图思路】的格式通过Markdown表格输出。
```
在一组系统提示词中，相对于编辑成一段的长文本，模型更容易识别具有物理边界的段落结构。因此建议使用Markdown标题、分隔符（如---、###）或特定的标签（如<Task></Task>）来组织内容。
```
# Role: [角色名称]
## Background
[描述为什么要执行这个任务]
## Goals
1. [目标1]
2. [目标2]
## Constraints
- [约束点1]
- [不要做的事]
## Workflow
1. Step 1: [第一步逻辑]
2. Step 2: [第二步逻辑]
## Output Format
[具体的排版要求]
```
结构化构建不仅是为了提升模型表现，更是为了可维护性。当输出不符合预期时，你可以快速定位是角色设定不够具体，还是约束条件存在冲突，从而进行针对性的优化，将提示词工程从“玄学”转化为科学的迭代过程。
##### 2. 提示词的版本管理
很多初学者在调Prompt时，常见问题不是不会写，而是改乱了。改了一句之后效果变好还是变差，说不清；模型参数变了还是提示词变了，也记不住。久而久之，优化过程变成了“玄学试错”。
因此，提示词工程必须建立版本管理意识。至少要做到以下几点：
每次修改只改一个关键变量，例如只改角色描述，或只改输出格式。
为每个Prompt版本编号，例如 v1.0、v1.1、v2.0。
记录修改目的，例如“增加拒答机制”、“优化表格输出”或“减少废话”。
固定测试样本，避免每次都换问题导致无法公平比较。
记录评估结果，包括准确率、完整性、格式稳定性、是否出现幻觉。

#### 一、智能客服回复优化
某智能门锁企业的客服部门希望上线一个客服Agent，用于自动处理用户的常见咨询。教师希望通过这个案例让学员理解：同一项任务，如果提示词不够清晰，模型输出会缺乏专业性和稳定性；如果提示词结构清晰，输出会明显更贴近业务场景。
用户输入示例如下：
```
我家门锁昨天还能正常联网，今天突然连不上 Wi-Fi 了。我已经重启过路由器，也换了手机热点测试，还是连不上。门锁型号是 X7-Pro，没有报错代码。
```
V1版提示词：
```
你是一个 AI 助手，请回答用户的问题。
```
图  在RAGFlow中设置简易提示词并提问
根据用户问题和V1版的基础系统提示词，思考如何利用所学的评估方法测试这组提示词的潜在问题，并用提示词工程为其添加约束，尝试构建新的提示词版本，并记录常见问题，如回答泛化、缺少分类、遗漏已知信息、缺少边界提示。反复测试提问，根据产生的问题迭代提示词。

```
5. 输出应便于客服坐席直接复制到工单系统中。

- 问题类别：
- 已知信息：
- 建议排查步骤：
- 是否需要补充信息：
- 是否建议转人工：
```

#### 二、会议纪要生成
某项目组希望让Agent根据会议内容自动生成纪要。通过这个案例要引导大家理解在和智能体的沟通中，怎么说比说什么更重要，因为用户的意图“帮我总结会议”看起来很简单，但实际业务中往往还要求区分决议、待办事项和责任人等。
用户输入示例：
```
会议内容：
本周我们讨论了智能巡检系统的上线安排。产品经理提出，第一阶段先上线设备异常告警功能；开发组表示接口联调还需要 3 天；测试组建议下周三前完成回归测试；最终决定 4 月 18 日进行第一批试点部署。张敏负责整理部署清单，李强负责跟进接口联调。
```
V1版提示词：
```
请帮我总结这段会议内容。
```
如上文所说，在实际业务中需要智能体对会议内容进行格式化总结，因此在构建系统提示词时，需要告知大模型用什么样的格式进行总结，具体可以参考V2版提示词示例：
```
你是一名项目管理助理，请根据会议内容生成正式会议纪要。
要求：
1. 提炼会议主题；
2. 明确会议达成的结论；
3. 列出待办事项、责任人和时间节点；
4. 不得遗漏具体日期和人名；
5. 输出要简洁，适合直接发送到工作群。
请使用以下格式输出：
## 会议主题
## 关键结论
## 待办事项
| 事项 | 责任人 | 截止时间 |
| --- | --- | --- |
```
分别运行两组关键词，观察模型是否会漏掉责任人和时间节点。再和其他同学的运行结果对比，看看是否有明显差异。将结果统计在实验结果表格中（见附录）。
通过这两个案例，希望学院理解以下几点信息：
1. 简单 Prompt 常常只能生成摘要，却不能直接形成协作结果；
2. 一旦要求责任人和截止时间等细节信息，Prompt 的业务导向就会明显增强；
3. 提示词工程不是语言修饰，而是业务信息提取设计。
### 【任务小结】
在本任务中，解决的是提示词工程的认知起点问题。完成任务后，学员应当意识到：提示词并不是模型交互中的附属品，而是 Agent 行为设计的核心入口。它决定了模型如何理解任务、如何分配注意力、如何组织推理、如何控制输出。提示词工程的目标不是把话说得更华丽，而是把要求说得更明确、更稳定、更高效。
只有理解了这一点，后续关于结构化 Prompt、Few-Shot、工具调用、规划与反思等技术，才有真正落地的基础。
