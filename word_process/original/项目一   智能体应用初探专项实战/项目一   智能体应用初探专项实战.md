#### 一、智能体的概念
##### 1. 工作流和智能体
工作流（Workflow）是一系列预定义的、有顺序的步骤，逻辑由开发者预先设定，强调流程固定、结果稳定、执行路径清晰。它适合标准化、重复性高、规则明确的任务。
智能体（Agent）则是以大语言模型为“大脑”，具备理解目标、规划步骤、调用工具、结合上下文进行动态决策的系统。它不是严格按照固定路径运行，而是在目标驱动下进行适度的推理和选择，因此更适合处理复杂、开放、信息不完整的任务。
从下可以清晰看出二者的区别：
维度
工作流（workflow）
智能体（Agent）
执行逻辑
路径由开发者做确定性预设
路径由 LLM 动态生成
灵活性
一切处理基于固定的预设方案
能处理模糊需求，并根据反馈调整策略
控制权
人类完全控制流程
LLM 自主决定执行步骤。
容错率
一个环节点出错，流程往往卡死
具备“反思”能力，尝试不同解决方案
复杂任务
适合标准化、可重复的任务
适合开放式、需要决策的复杂任务
代表比喻
必须在轨道上行驶的一列火车
有目标，根据路况实时打方向盘的赛车手
##### 2. 智能体的定义和能力框架
关于智能体的定义，随着业界对相关技术研究的深入而不断调整，目前业界最权威、引用最广泛的定义框架主要来自 OpenAI 的主管 Lilian Weng 的文章，以及吴恩达（Andrew Ng）对智能体设计模式的总结。我们可以通过比对这些定义架构的相同共和差异来进一步理解智能体。
最经典框架：“LLM + P.M.T”模型
OpenAI 的应用研究主管 Lilian Weng 在其文章 《LLM Powered Autonomous Agents》 中提出了一个被广泛认可的公式：
Agent = LLM（大脑）+ 规划（Planning）+ 记忆（Memory）+ 工具使用（Tool Use）
规划是指智能体能够将复杂的任务拆解为更小的、可管理的子目标。并且对过去的行为进行自我批评和反思，从错误中学习并改进策略；记忆是模仿人类认知的上下文及数据处理方式，分为短期记忆：利用模型的上下文窗口记录当前的对话历史和推理过程；和长期记忆：通过外部向量数据库实现，能够根据需要检索长期存储的信息；工具使用则是指智能体意识到自己能力的边界，通过调用外部 API 获取实时信息（如搜索）、执行计算（如计算器）或操作软件（如写代码），进而解决相关问题的能力。
吴恩达提出的四大设计模式
吴恩达在 2024 年多次演讲中强调，与其追求更大的模型，通过一次性实现完美输出，不如通过智能体工作流（Agentic Workflow）迭代输出结果，从而提升表现。他总结了四种核心能力模式：
反思 (Reflection)：智能体检查自己的工作，寻找改进方法。例如，写完代码后自己运行一遍，发现报错后自行修复。
使用工具 (Tool Use)：虽然与 Lilian Weng 重合，但吴恩达更强调智能体作为“意图触发者”，根据环境判断何时该使用什么工具。
规划 (Planning)：能够自主决定达成目标所需的步骤序列，且能根据执行过程中的中间结果动态调整路径。
多智能体协作 (Multi-agent Collaboration)：不同的智能体扮演不同的角色（如：一个写代码，一个负责测试），通过对话和分工共同完成任务。
学术与通用定义：认知神经科学视角
在更广泛的 AI 研究中，智能体被定义为具备 感知—推理—行动 循环的实体：
感知 (Perception)：将非结构化数据（文本、图像、语音、传感器数据）转化为模型可理解的表示。
推理 (Reasoning)：基于当前目标和环境感知，通过大模型的逻辑推理选择最优策略。
行动 (Action)：作用于环境，改变状态。
结合这些对智能体的相关定义和框架构建，得出智能体核心能力的图谱如表。
核心模块
关键能力描述
大脑 (Brain)
逻辑推理、意图识别、语言理解
记忆 (Memory)
短期上下文缓存、长期知识检索
规划 (Planning)
任务拆解、动态路径调整、自我纠错
工具 (Tools)
调用API、代码执行、控制物理设备
执行 (Action)
将思考结果转化为外部世界的实际影响
无论表述如何变化，“感知—记忆—规划—工具—行动”五大能力始终是智能体系统的核心支柱。感知让智能体“看得见”，记忆让它“记得住”，规划让它“想得清”，工具让它“做得到”，协作让它“连得通”。理解这一共性，是掌握智能体开发的第一步。
#### 二、RAGFlow平台初识
RAGFlow是一个开源的大语言模型（LLM）应用开发平台，旨在简化和加速生成式AI应用的创建和部署，为开发者提供了一个用户友好的界面和一系列强大的工具，通过可视化编排、模块化设计和丰富的功能组件，使他们能够快速搭建多种类生产级的AI应用。
##### 1. 从langchain到RAGFlow
在RAGFlow等低代码平台出现之前，开发者构建AI应用主要依赖LangChain等编程框架。LangChain作为模块化的开发者工具包，需要Python或JavaScript编程经验，学习曲线较陡，适合深度定制和复杂场景开发。
下方是为了实现最小对话智能体工作流的langchain开发代码案例：
import os
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_community.chat_message_histories import ChatMessageHistory
# 1. 配置模型 (会自动从环境变量读取 OPENAI_API_KEY)
model = ChatOpenAI(model="gpt-3.5-turbo")
# 2. 定义包含历史占位符的提示词模板
prompt = ChatPromptTemplate.from_messages([
("system", "你是一个简洁的助手。"),
MessagesPlaceholder(variable_name="history"),
("human", "{input}")
])
# 3. 构建链 (LCEL 语法)
chain = prompt | model
# 4. 封装记忆逻辑（这是为了能自动管理不同用户的对话记录）
store = {}  # 内存存储
def get_session_history(session_id: str):
if session_id not in store:
store[session_id] = ChatMessageHistory()
return store[session_id]
with_history_chain = RunnableWithMessageHistory(chain, get_session_history, input_messages_key="input", history_messages_key="history")
# 5. 测试对话
config = {"configurable": {"session_id": "user_1"}}
resp1 = with_history_chain.invoke({"input": "你好，我叫小明"}, config)
resp2 = with_history_chain.invoke({"input": "我叫什么名字？"}, config)
print(resp2.content) # 输出：你叫小明。
虽然在逻辑上并不复杂，但是对初学者不够友好，且迭代开发较为繁琐。与之相对，RAGFlow提供低代码拖拽界面和可视化工作流设计，大幅降低了AI应用开发的门槛，适合快速原型验证和企业级快速部署。两者的本质区别在于开发范式：LangChain是写代码编排智能体，如图 RAGFlow是通过拖拽节点的方式编排工作流，在工作流中嵌入智能体或大模型实现智能体工作流的开发。对于初学者而言，RAGFlow的可视化方式能够让我们更快理解智能体工作流的逻辑结构，而不必被代码细节干扰。
##### 2. RAGFlow工作流
工作流是一种将一系列任务或操作按照一定的顺序和规则自动化执行的方法。在RAGFlow中，编辑智能体工作流通过连接不同的节点，利用大语言模型的能力，实现复杂任务的自动化处理。这些节点可以包括数据输入、处理、输出等多个环节，用户可以根据自己的需求自由组合和配置，实现对话、搜索、RAG管理以及智能体等多种功能构建。
RAGFlow工作流的特点如下：
可视化编辑：RAGFlow提供了直观的可视化工作流编辑器，用户可以通过拖拽节点和连线的方式轻松构建自己的工作流。
灵活性：RAGFlow支持多种节点类型，包括大语言模型节点、知识库检索节点、条件判断节点等，用户可以根据自己的需求自由组合和配置。
开放性：RAGFlow支持多种大语言模型API调用，包括DeepSeek、GPT、Ollama等，用户可以根据自己的需求选择合适的模型。同时，RAGFlow也支持私有化部署，保护用户的数据安全。
##### 3. RAGFlow工作流的构建步骤
RAGFlow中智能体菜单下的工作流（workflow）和对话流（chatflow）两种工作流应用的区别是工作流面向单轮自动化编排任务，而对话流将记忆内置为上下文变量从而支持多轮对话工作。但不论哪种工作流应用，构建步骤如图 ：
创建应用：在RAGFlow平台上创建一个新的应用，选择工作流类型。
设计工作流：使用可视化工作流编辑器，拖拽节点和连线，设计自己的工作流。
配置节点：对每个节点进行配置，包括输入参数、输出参数、模型选择等。
测试工作流：在RAGFlow平台上测试工作流的运行情况，确保每个节点都能正确执行。
发布工作流：测试通过后，将工作流发布到生产环境，实现自动化处理。
通过RAGFlow，学员可以以较低门槛完成从设计搭建到调试发布的完整AI应用平台建设。

##### 3. 简易智能体工作流的最小组成

以上4个环节构成了一个最小可运行智能体工作流。它的本质是“用户输入→约束引导→模型推理→人工评判”的闭环。虽然结构简单，但已经具备了智能体工作流的两个核心要素：

在实际开发中，可以从这个最小结构出发，逐步增加节点：例如加入意图识别分支、知识库检索、代码计算等，从而演化为完整的工作流或智能体。这种由简入繁、迭代优化的思路，也是工程化落地的重要方法论。
##### 4. RAGFlow工作流的核心组件
基于上一节提出的“用户输入→系统提示词约束→模型生成→人工评估”最小可运行结构，在RAGFlow中搭建这一流程只需用到以下核心组件：
开始节点
开始节点是所有工作流的入口。在RAGFlow的可视化工作流设计器中，每个工作流都以开始节点为起点。该节点负责接收用户的输入数据，用户的问题将通过这个节点传入后续节点。在 RAGFlow的工作流中，开始节点提供的这三个功能：对话（Chat）、任务（Job/Task）和网络钩子（Webhook），本质上定义了这个智能体的启动方式和交互模式。
1) 对话（Chat）——聊天机器人模式
如图 ，这是最常用的模式，适用于构建交互式智能体。
工作逻辑：它是双向、实时、有上下文的。用户说一句话，智能体回一句话。
输入内容：主要变量通常是用户的提问（query）。
特有属性：
会话管理：它能处理聊天记录（Memory），让智能体记得你上一句话说了什么。
交互界面：这种模式通常直接对接对话框界面。
使用场景：
企业内部客服机器人。
个人知识库助手。
角色扮演（Roleplay）机器人。
2) 任务 (Job / Task)——批处理/自动化模式
如图 ，这种模式通常是单次执行、流程导向的自动化处理。
工作逻辑：接收一个特定的输入，按照你设计的逻辑跑完整个流程，最后给出一个结果。它不强调来回对话，而是强调完成任务。
输入内容：通常是结构化的数据或参数，比如一个特定的文档ID、一个待总结的网页链接等。
特有属性：
无状态/单次执行：它通常不关心历史聊天记录。
高效性：适合处理大批量的、重复性的逻辑。
使用场景：
文档自动化处理：比如你上传一个100页的报告，触发一个任务模式的工作流，让它自动提取关键数据并生成 Excel。
定时报表生成：每天凌晨自动检索知识库，总结昨天的信息。
3) 网络钩子(Webhook)——系统集成模式
如图 ，这是为自动化系统准备的接口模式。它让RAGFlow能够被其他软件调用。
工作逻辑：RAGFlow会生成一个URL地址。每当外部系统向这个地址发送一个HTTP请求时，工作流就会启动。
输入内容：由外部系统传过来的JSON数据包。你可以自定义解析这些数据。
特有属性：
被动触发：智能体在后台静静等待，直到接收到外部信号。
跨系统联动：它是打破RAGFlow与其他软件之间壁垒的桥梁。
使用场景：
联动钉钉/微信：当用户在钉钉群里@机器人时，钉钉服务器发一个Webhook给RAGFlow，RAGFlow 处理完后再回传。
自动化流水线：比如 GitHub 有代码更新了，触发Webhook让RAGFlow自动读取新代码并更新技术文档知识库。
大语言模型节点
LLM节点是整个工作流的大脑。如图 ，在该节点中，你需要完成三件事：①选择要使用的大模型（如GPT-4、DeepSeek、Qwen等）；②配置系统提示词（System Prompt），对模型的角色和行为进行约束；③调整模型参数（如Temperature），控制输出的确定性与多样性。对于本任务的最小工作流，只需要配置好系统提示词，并将开始节点传入的用户问题作为上下文变量输入到LLM节点即可。
输出节点
输出节点负责输出LLM节点生成的最终回答，如图 。在简单问答工作流中，通常只需要将LLM节点的输出直接连接到结束节点，工作流执行完毕后返回结果。

### 【知识储备】
#### 一、什么是提示词工程
提示词工程（Prompt Engineering）是指围绕LLM或 Agent 系统的输入指令进行设计、组织、约束与优化，从而让系统更稳定地完成目标任务的方法。它不是简单地提问技巧，而是一种面向结果的交互设计方法。
在传统的软件系统中，开发者通过代码定义执行逻辑；而在智能体工作流系统中，提示词往往承担了半结构化程序的作用。它不仅告诉模型“做什么”，还告诉模型“以什么身份做”“依据什么信息做”“按照什么规则做”“最后以什么格式输出”。因此，提示词本质上是在为智能体编写行为说明书。
##### 1. 从LLM到Agent：提示词如何驱动决策
LLM 本身擅长语言理解与生成，但它并不会天然知道当前系统的目标、边界和优先级。Agent 则是在 LLM 基础上叠加了记忆、规划、工具调用和行动能力的系统。此时，提示词起到的作用就不再只是发起一次对话，而是持续塑造Agent的决策逻辑。
例如，在一个客服智能体中，提示词可以规定：
你是售后服务助手，不是销售顾问。
先判断用户问题类别，再决定是否查询知识库。
若知识库无答案，不允许编造，必须明确告知“暂无法确认”。
输出必须包含“问题判断”、“处理建议”以及“是否需要人工介入”三个字段。
这几句话看似自然语言，实则已经在约束智能体的角色、流程、容错机制和输出结构。提示词写得越清晰，智能体的行为越可控；提示词写得越模糊，智能体越容易漂移。一个优质提示词，通常要兼顾以下三个目标：
确定性
确定性并不是要求模型每次一字不差，而是要求模型在相同输入下尽量给出风格稳定、结构稳定、结论边界稳定的回答。对于企业级智能体而言，稳定性往往比偶尔的一次惊艳回答更重要。
逻辑性
逻辑性是指提示词要让模型清楚：先做什么，再做什么；依据什么判断；遇到异常怎么办；什么情况下该拒绝回答。逻辑清楚，模型的中间推理和最终输出才不容易跳步。
效率
效率既包括模型响应效率，也包括开发效率和 Token 成本。一个优质提示词不应堆砌无关描述，而应在有限上下文内，把最关键的约束表达清楚。
如图 所示，可将三者关系概括为：确定性保证可用，逻辑性保证可信，效率保证可落地。

#### 二、LLM的工作原理简述
要做好提示词工程，不能只会写指令，还要理解模型为什么会这样响应。大语言模型的核心机制并不是理解了真实世界后再回答，而是根据已有上下文，预测下一个最可能出现的词或 Token。正因为它是概率生成，所以提示词的表达方式会显著影响结果分布。
##### 1. 预测机制与概率分布
当我们输入一句提示词时，模型会把整段上下文编码成内部向量表示，然后基于训练中学到的模式，预测下一个 Token 的概率分布。如图 ，在“今天天气很”之后，模型可能会认为“好”“冷”“热”“不错”等词都有不同概率。最终输出什么，取决于上下文、模型参数以及采样方式。
这意味着模型输出不是从零开始编一个答案，而是基于上文判断下文概率最高的延续。因此如果提示词模糊，模型会在更多可能性中摇摆，输出更不稳定；反之如果提示词明确，概率空间被压缩，模型更容易落在期望答案附近。
##### 2. 添加限定词约束大模型
因此，提示词工程的核心之一，就是通过清晰的上下文和明确的约束，把模型的概率分布“收紧”到更可控的区域。许多初学者会认为，只要把任务说出来就够了。实际上，在大模型场景中，“说什么”只是目标层，“怎么说”决定了模型如何理解这个目标。
例如，下面两个提示词表面上都在要求总结文章：
V1：
帮我总结一下这篇文章。
V2：
你是一名面向企业管理者的信息分析助手。请阅读下文，并提炼出：
1. 核心观点；
2. 支撑观点的关键事实；
3. 对企业决策的启示。
输出控制在 200 字以内，使用正式、客观的书面语。
二者的差别不在是否要求总结，而在于第二种写法明确了身份、读者、提取维度、长度和风格，从而显著提升了输出质量。换句话说，模型并不是听懂一句话就能自动补全所有隐含要求，它更像一个极其强大但需要明确边界的执行者。提示词写法越清楚，模型越容易朝正确方向生成。
##### 3. 使用few-shot提示
更进一步，除了明确身份、维度、长度和风格外，还有一种更直接、更强大的“怎么说”方式：给模型提供示例（few-shot）。
仍以“总结文章”为例。即使你已经写好了第二种提示词（明确了身份、读者、提取维度和风格），模型在处理不同文章时，依然可能在某些细节上偏离预期——例如把“核心观点”写成了两句话，或者在企业启示部分写得过于空泛。这时，你可以在提示词中直接放入一个真实的输入输出示例，让模型照模板来回复。

#### 三、结构化提示词与版本管理
##### 1. 结构化的系统提示词
在构建大模型的系统提示词时，结构化设计是确保模型输出稳定性、准确性和专业性的核心。相比于碎片化的指令，结构化的提示词能够为模型建立一个清晰的逻辑框架。其核心思想是将复杂的任务拆解为若干个标准化的模块。通过清晰的分隔符和逻辑层次，引导模型更精准地理解意图。一个成熟的结构化提示词通常包含以下五个核心模块：
角色设定 (Role)：定义模型的身分。
你是一位拥有10年经验的资深资深文案策划专家，擅长撰写高转化率的社交媒体推文。
背景信息 (Context)：提供任务的上下文或目标受众。
我们正在推广一款针对职场新人的自律打卡App，其核心卖点是‘趣味化社交’。
任务目标 (Task)：明确模型需要执行的具体动作。
请根据产品卖点，撰写3条不同风格的推文文案。
约束与规则 (Constraints)：规定“能做”和“不能做”的边界。
语言风格需轻松活泼；禁止使用虚假宣传词汇；每条文案长度不超过150字。
输出格式 (Output)：规定返回结果的形式。
请按【风格关键词】、【推文内容】、【建议配图思路】的格式通过Markdown表格输出。
在一组系统提示词中，相对于编辑成一段的长文本，模型更容易识别具有物理边界的段落结构。因此建议使用Markdown标题、分隔符（如---、###）或特定的标签（如<Task></Task>）来组织内容。

##### 2. 提示词的版本管理
很多初学者在调Prompt时，常见问题不是不会写，而是改乱了。改了一句之后效果变好还是变差，说不清；模型参数变了还是提示词变了，也记不住。久而久之，优化过程变成了“玄学试错”。
因此，提示词工程必须建立版本管理意识。至少要做到以下几点：
每次修改只改一个关键变量，例如只改角色描述，或只改输出格式。

固定测试样本，避免每次都换问题导致无法公平比较。
记录评估结果，包括准确率、完整性、格式稳定性、是否出现幻觉。

### 【知识储备】
#### 一、从提示词到工作流
在项目一中，我们通过提示词工程（Prompt Engineering）解决了“如何告诉模型做什么”的问题，但在真实的Agent系统中，仅有一个优质Prompt仍然不够。因为企业场景中的任务往往不是一步完成的，而是要经历输入接收、意图判断、知识检索、信息补全、工具计算、结果格式化、状态保存等多个环节。
提示词可以说是节点的行为说明书，而Workflow/Chatflow则是这些说明书被组织起来之后的执行流程。如果没有工作流，模型虽然会回答，但不会稳定地接收变量、判断分支、调用工具，也不会在多轮对话中持续保持上下文。
因此，学员需要建立一个新的视角：
Agent不是一个节点，而是一条链路。
节点不是随便堆砌，而是要承担明确职责。
变量不是“临时文本”，而是流程里的数据载体。
多轮对话不是依赖模型本身的上下文记录，而是系统显式地管理会话和历史。
很多初学者刚接触工作流平台时，容易把它理解成“把几个Prompt连起来”。这种理解并不完整。工作流中真正重要的，不只是每个节点说了什么，更包括：
上一个节点输出了什么字段。
下一个节点期待接收什么类型的数据。
条件分支依据什么变量做判断。
哪些信息要进入上下文，哪些不能进入。
哪些结果需要持久化到会话中，哪些只用于本轮计算。
工作流设计的核心不是节点越多越复杂越高级，而是每个节点各司其职，节点之间传得稳、接得住、判得清。
#### 二、构建工作流的“积木”：组件功能和选择
在大多数Agent平台中，一个工作流通常由若干基础节点构成。理解这些节点的角色边界，是后续搭建稳定流程的前提。在本任务中，我们继续基于RAGFlow进行智能体工作流的开发。因此，我们要继续学习之前没讲到的工作流组件。
##### 1. 开始/结束节点：输入输出变量的定义
如图 ，开始节点（Start）负责声明这条工作流“从哪里拿数据”。结束节点（End）负责声明这条工作流“最后产出什么”，如图 。看似简单，实际上它们决定了整个流程的数据边界。
开始节点决定系统从哪里接收原始输入，它可能接收用户文本、上传文件、系统时间、业务参数或会话标识。结束节点则决定流程最终交付什么，它可能是一段回复文本，也可能是一组结构化字段，或者是一份供外部系统直接消费的对象。实训中许多问题，并不是中间推理出了错，而是起点没有定义清楚、终点没有约束稳定，导致整个流程虽然看起来完成了运行，却在某一节点处“卡死”，无法进入后续系统。
如果把工作流比作一条生产线，那么开始节点定义的是设定原材料的规格，结束节点定义的是最后输出的成品规格。如果两端设定不清晰，中间过程的管理一定是混乱的。
##### 2. LLM 节点：核心推理单元
LLM 节点是工作流中的语义推理核心，如图 。它最擅长处理自然语言理解、意图识别、信息抽取、开放式分类、文本归纳和自然语言生成等任务。凡是必须依赖语义理解与上下文推理的工作，都适合交给LLM节点来完成。
但一个成熟的系统绝不会让模型包办一切。规则明确的逻辑判断，应由IF/ELSE 等控制节点处理；数值计算、字段清洗、批量处理、格式标准化等工作，更适合交给代码节点完成；私有知识查询，则应交给知识库节点处理。对学员来说，本节最重要的，不是记住智能体节点能做什么，而是学会判断哪些任务不该让智能体去做。
##### 3. 代码执行节点：使用 Python/Node.js 处理复杂数据
代码节点（图 ）可以让用户编写代码实现自定义功能，适合承担程序化的工作，比如对数据的清洗、合并、增删或解析。通常我们会使用该节点处理数据，为后续节点提供结构化表达的对象。
知识检索节点与代码执行节点，分别代表Agent与外部知识能力、程序能力的协作方式。前者让回答建立在企业真实资料之上，后者则承担那些程序比模型更稳定、更可验证的任务，例如统计、规范化、阈值判断和JSON处理。
##### 4. 条件分支节点：意图路由分解
如图 ，在RAGFlow中提供了两种分解路由的方式，一种是传统的条件分支，通过设置条件变量来判断后续运行哪条分支。另一种是通过内置大模型的问题分类器，将输入的文本通过大模型进行语义分析，再根据设定的路由方案选择后续分支。
条件分支节点适合承接规则明确的流程分叉。例如，在售后客服的智能体流程中，设置两个变量intent代表用户意图，need_clarification判断已获取的信息是否充足，可以设置以下分支：
1) 如果intent=查询设备状态，进入知识库查询分支。
2) 如果intent=报修申请，进入补充设备编号分支。
3) 如果need_clarification=true，进入追问分支。
4) 如果intent=重置会话，进入记忆清空分支。
在一般的开发流程中，我们会采用LLM负责判断意图，IF/ELSE负责执行路由。虽然RAGFlow提供了可以直接用LLM判断意图并执行路由的问题分类节点，但在实际开发过程中这两者最好分开，不要让一个LLM节点一边判断、一边自己决定整条流程怎么走，可控性会明显下降。
##### 5. 变量聚合节点：多路由变量同一
变量聚合器（Variable Aggregator）常用于把多个分支、多个节点或多个迭代结果汇总到一起，方便后续统一处理。它的价值很大，但也是工作流里最容易出现问题的节点之一。
从名称看，学员可能会误以为该节点可以实现变量的拼接，但实际上变量聚合器只会将传入该节点的第一个有效变量作为输出结果。因此该节点多伴随在条件分支路由的后端，用于将两条路由合并，但实际上只会从其中得到一个变量的结果作为后续节点的统一处理变量。RAGFlow的变量聚合器内置变量格式检测，如果和设定变量类型不匹配的变量无法被检测到，如int和string。但如果同样是string的变量不会有进一步检测，这也导致变量聚合器接收到的变量可能是不同结构，如果没有进一步处理为统一格式，很容易导致后续节点因为格式不匹配等问题产生报错。
如图变量聚合器聚合的常用方法，在前置节点被条件分支分开的两条路由，分别导向智能体节点和代码执行节点，二者的输出变量汇聚到变量聚合器后，被输出为Group0变量。但根据前置路由我们会发现，在智能体和代码执行两个节点中，只会有一个符合前置条件分支的节点被执行，而另一个没有被执行，所以是空变量。因此Group0的结果是二者之一，但如果通过某些方式，设置汇入变量聚合器的两个变量都有效，此时变量聚合器返回的是从上到下的第一个有效变量，在下图中是来自智能体_0节点的content变量。
变量聚合器和分支节点虽然更像辅助组件，但它们往往直接决定流程稳定性。很多真实问题并不出现在模型本身，而出现在这些节点之间，例如输出结构不一致、聚合结果类型混乱、数组层级出错、模板引用空字段等。因此，这一节要向学员传达的是：工作流不是节点展示，而是职责组织；节点设计的专业性，最终体现在整个系统能否稳定协作。
除了上述节点外，RAGFlow还有提供模板转换、循环和迭代等方法，在本节中不再一一介绍，学员有兴趣可以自行学习并应用在自己的智能体工作流开发中。
#### 三、变量管理与数据传递
##### 1. 变量管理
如果说节点是工作流的器官，那么变量就是工作流中的血液与血管。一个节点是否能正常工作，很大程度上取决于它当前拿到了什么数据；一个工作流是否稳定运行，本质上取决于这些数据能否在不同节点之间被正确地传递、命名、解释和消费。很多表面看起来像模型发挥不稳定的问题，实际根因恰恰是变量没有传对、传全，或者字段名称、类型、作用域存在不一致。
上下文管理是变量管理中最容易被误解的一部分。很多初学者天然会觉得，把信息给模型给得越多越好，似乎上下文越长，系统越聪明。但在工程实践中，上下文的核心原则并不是尽可能多，而是够用即可。如果传入的信息过少，模型会表现为失忆、误判或重复追问；如果传入的信息过多，则会增加噪声、抬高Token成本，并掩盖真正关键的变量。更专业的做法，是围绕当前节点的职责，有选择地传入必要信息。也就是说，变量管理不是单纯的在流程中添加或删减变量，更是一次上下文裁剪与信息组织能力的训练。
##### 2. 变量契约
学员需要形成“变量契约”的概念。所谓变量契约，是在搭流程之前，就先明确关键变量的名称、类型、来源、含义和是否必填。它看起来像一种额外的文档习惯，但本质上是工程化流程设计的基础。变量契约的价值，在于减少字段混乱、提高团队协作效率、降低后期维护成本，并让调试过程变成检查字段，通过比对预期值来调整工作流。

#### 四、对话型工作流
多轮对话是很多Agent场景的核心能力，例如客服咨询、报修受理、知识答疑、任务协办等。要实现多轮，不是简单把工作流跑很多次，而是要引入“会话状态”。
##### 1. Workflow vs. Chatflow
工作流（Workflow）更适合一次性任务，如总结一份文档、处理一次表格数据等，这类流程通常是单次执行即结束，执行完成后，流程本身并不自动保留历史状态。每执行一次，通常只接收当前输入，产出当前输出，流程中不会自动知道上一轮执行的记录。所以，当业务需要“追问、补槽、连续确认、上下文延续”时，单纯使用无状态Workflow往往不够。
对话流（Chatflow）则用于持续对话场景。系统会自动维护会话ID、历史消息和部分上下文，使得用户的多轮输入能够被视为同一段连续交互。因此Chatflow可以理解为带状态的工作流。
##### 2. 会话记忆机制与配置
会话记忆机制决定了Agent在多轮对话中是否具有连续性。没有记忆，多轮对话就会退化为很多次单轮问答；记忆配置不当，则可能引发信息污染、Token膨胀或答非所问。
需要特别说明的是，不同平台对“记忆”的实现方式并不完全相同。有的平台提供独立的记忆组件，有的平台则是在LLM节点中配置历史注入，有的平台把会话历史管理放在Chatflow运行时中自动处理。因此，从更专业和更通用的角度看，本节讨论的重点应当是“会话记忆机制”，而不只是RAGFlow或某个平台上的某一个具体节点。
在很多平台中，记忆能力不是自动产生的，而是需要在LLM节点中显式配置对话历史变量，或启用对应的历史注入选项。其本质，是让模型在当前轮输出内容生成时，看见之前若干轮的消息。当然很多大模型内置有记忆功能，在简单的工作流对话中，可以发现大模型能够识别到之前对话的内容。但这只是大模型节点自身的记忆功能，它所认识到的不是整个工作流会话的记忆。如果你的问题是它前面或者后续节点的工作内容，那会发现大模型就束手无策了。但在实际的项目实施中，记录整个会话过程的历史是工作流搭建不可或缺的一环。常见配置思路是在系统中显示指定一个历史变量，例如`history`。再决定它所携带的用户信息，并在流程中显式更新，以及在提示词中明确要求模型结合该变量理解当前问题：
你正在与用户进行连续对话，请结合以下历史对话与当前输入进行判断：
【历史对话】
{{history}}
【当前问题】
{{sys.query}}
这种写法把历史记录和当前问题区分开了，让模型关注点主次分明，避免把所有内容混成一团。
##### 3. 意图识别、补槽与会话路由
在企业Agent中，真正决定系统效率的，往往并不是语言表达是否自然，而是它能否快速判断当前输入属于什么任务、还缺什么信息、下一步应该往哪里走。也就是说，多轮系统的关键，不只是连续对话能力，而是业务推进能力。这就需要引入意图识别、补槽机制和会话路由。
意图识别的本质，是把用户自然语言映射成业务动作。用户说“帮我报修”“巡检标准温度是多少”“设备编号是AC-204”“不用继续了，重新开始”，从人类角度看只是不同句子，但在系统内部，它们对应的却是不同流程入口。成熟的设计通常会先让LLM节点完成语义判断，再输出结构化结果。这样的设计把“理解”与“执行”分离开来，既保留了模型对自然语言的适应能力，也保证了流程整体的可控性。
在任务型对话中，补槽机制（Slot Filling）尤其重要。许多业务任务在信息不完整时，并不能直接生成结果。报修需要设备编号、位置、故障现象和联系人；预约需要时间、地点和对象；审批需要事项、理由和附件。补槽并不是多问几句，而是一种结构化的信息收集过程。一个专业的补槽系统，必须先知道完成当前任务至少需要哪些参数，再根据当前状态判断还缺少什么，并且在每一轮只追问最关键的少数字段，而不是一次性抛出大量泛化问题。补槽的本质不是“增强聊天感”，而是“推动业务向完成状态推进”。
与之相伴的，是新话题识别与会话重置机制。真实用户并不会严格沿着系统预设路径交互，他可能在补充报修信息时突然转去问知识问题，也可能直接中断当前任务重新开始。如果系统不能正确识别这些行为，就会出现旧状态污染新任务的问题：知识问答被错误地当成报修信息补充，旧槽位被错误带入新流程，或者系统继续追问已经无关的字段。因此，有必要让智能体知道如何“继续当前任务”，以及如何“结束当前任务”，或者在不同任务之间切换。对企业级智能体来说，这种话题边界感并不是锦上添花，而是系统长期可用的重要前提。

# Role 你是一个高级意图识别专家，负责分析设备运维场景下的用户需求。 # Task 1. 分析用户当前输入的意图（intent）： - `repair_request`: 发起报修或补充报修信息（如提供设备号、电话等）。 - `qa_query`: 询问设备参数、故障代码含义、操作标准等知识性问题。 - `reset_session`: 用户明确表示“重新开始”、“换个话题”或“不报修了”。 2. 提取报修槽位（slots）： - device_id (设备编号) - location (位置) - fault_desc (故障现象) - contact_name (联系人) - contact_phone (联系电话) # Rules - 结合历史对话 /判断：如果用户在补充信息，intent 应保持为 `repair_request`。 - 如果用户突然问知识类问题，intent 识别为 `qa_query`。 - 必须以 JSON 格式输出，不要包含任何解释文字。 # Output Format { "intent": "repair_request" | "qa_query" | "reset_session", "slots": { "device_id": "提取的值或 null", "location": "提取的值或 null", "fault_desc": "提取的值或 null", "contact_name": "提取的值或 null", "contact_phone": "提取的值或 null" }, "is_complete": true | false (当所有必填槽位都不为 null 时为 true), "topic_switched": true | false (如果用户从报修中途转向知识问答，设为 true) }
在样例设置里，限定了大模型的输出结果为一个json变量，这对后续拆解变量有很大帮助。
但是，在RAGFlow中，条件节点无法直接获取json变量中的内容，因此我们需要在LLM节点和条件节点之间插入代码节点，命名为“意图分割”，通过图 1-1- 31执行代码的方式拆解用户意图变量intent：
在代码节点首先将变量输入变量设置为来自意图分析节点的content，这是一个string格式的变量。要注意默认的代码节点给出了两个变量，如果无需使用第二个需要给他删掉；或者还需要使用更多变量可以添加。但其中的内容是按照json格式编写的，因此可以通过导入并加载json格式的方式获得intent，编辑的代码如下：

import json

接下来设置报修这条路由的细节，如图 ，我们需要从意图分析节点获取填充工单需要的槽位信息，如法炮制使用代码节点拆解表单内容slots，并设置该节点输出变量为slots。

步骤十一：测试工作流
为了验证我们搭建的工作流是否可以正常运行，我们可以按照如下的测试流程进行检验。
第一组：纯知识问答测试
目标：测试 Categorize 节点是否能准确识别问答意图，且 LLM 是否能正常输出知识。
用户输入：“空压机巡检标准温度是多少？”
预期输出：直接回答 70°C - 95°C，不应出现报修相关的询问。
用户输入：“设备报警灯闪烁代表什么？”
预期输出：解释红色和橙色闪烁的含义。
第二组：标准报修补槽测试
目标：验证系统是否能识别缺失信息，并分次收集，且不重复询问已提供的信息。
用户输入：“我这台泵坏了，一直漏油，帮我报修。”
预期输出：内容应确认为漏油，并追问：设备编号、位置、联系人、电话。
用户输入：“设备号是 WP-001，在三号仓库。”
预期输出：内容应显示已记录设备号和位置，仅追问：联系人姓名和电话。
用户输入：“我是张工，电话 13912345678。”
预期输出：内容应呈现完整的报修摘要（包含 WP-001、三号仓库、漏油、张工、电话），并询问是否提交。
第三组：话题切换冲突测试
目标：验证在报修过程中，用户突然问问题，系统能否平滑切换。
用户输入：“空压机一直报警，帮我报修。”
预期输出：【补槽中】，请提供编号、位置、故障描述等。
用户输入：“设备编号 AC-204。对了，顺便问下，报警代码 E17 是什么意思？”
预期输出：开头必须有“已为您切换到咨询模式。关于您问的...”，然后解释 E17 的含义。
用户输入：“好，我知道了。我在二号车间，报修吧。”
预期输出：识别到用户回到了报修话题，继续收集剩余信息。
第四组：重置会话测试（验证 Reset 逻辑）
目标：验证用户明确要求重新开始时，系统是否重置。
用户输入：“我这台泵坏了，帮我报修。”
预期输出：进入报修补槽流程。
用户输入：“算了，不报修了，重新开始，换个问题。”
预期输出：进入重置分支，回复“已为您重置当前会话...请问有什么可以帮您？”
用户输入：“空压机巡检标准是什么？”
预期输出：正常回答知识点，且不应再提起刚才那台“坏了的泵”。
### 【任务小结】
本任务的核心是帮助学员建立工作流思维：Agent 的稳定性，不只来自模型，也来自节点职责是否清晰、变量传递是否准确、控制流是否合理、记忆管理是否克制。本任务解决的问题是“Agent 如何在系统里按流程做”。学员应逐步形成这样的意识：
1. Prompt 决定单点行为，Workflow 决定系统执行。
2. 变量是工作流的数据血管，不是随手写的占位符。
3. Chatflow 的关键价值，在于把“会话状态”纳入系统设计。
4. 真正可用的 Agent，不只是答得像人，更要流得顺、接得住、记得清。
